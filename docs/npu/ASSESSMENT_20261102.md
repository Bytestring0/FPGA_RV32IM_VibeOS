# 项目性能优化、DDR DMA 与 I/D Cache 评估

日期：2026-11-02
性质：基于当前源码与已有报告的只读评估，供后续实施决策使用。
范围：CPU＋NPU＋DDR＋SD，以及两份外部模型分析的适用性。

## 一、总体判断与工作优先级

可以采用“先优化性能架构、完成 I/D Cache 的功能与一致性闭合，再集中解决最终时序”的顺序。

前一阶段通过功能仿真、周期统计和整图对照确认优化是否有效；实际板端 token/s 仍须在最终时序闭合、上板后确认。性能优化期间同步检查数值与任务质量，避免最后才发现提速版本无法完成真实工具任务。

两份分析的大方向有参考价值，但不能直接照着修改。其中，第一份关于 Delta q/k 缩放的核心诊断存在数学错误；第二份将若干尚未实现的架构建议与当前已有能力混在一起。

本次只查阅和评估，未修改工程源码。本文件中的建议不代表功能已经实现，也不代表新增实施授权。

## 二、NPU 是否已经直接从 DDR 搬运数据

**已经实现。CPU 不需要逐字搬运模型权重给 NPU。**

当前通路为：

```text
CPU ──配置寄存器、提交任务、维护缓存
                    ↓
DDR ←→ DDR控制器/仲裁器 ←→ 矩阵NPU、tensor NPU
```

矩阵和 tensor 引擎都有独立的 DDR 请求、响应接口，与 CPU Cache 通过仲裁器共享 DDR。CPU 仍负责调度和缓存一致性维护，部分模型适配操作仍会产生 staging 复制；这些开销不等于“权重必须由 CPU 逐字送入 NPU”。

| 能力 | 当前情况 |
| --- | --- |
| NPU 直接从 DDR 读取权重、激活并写回结果 | 已实现 |
| 连续预取权重，让 DDR 搬运与计算充分重叠 | 尚未实现完整流水 |
| SD 卡直接 DMA 到 DDR | 尚未实现，仍是 SPI/PIO |

后续重点应是提高现有 DMA 的供数效率，而不是重新建设“NPU 直连 DDR”。SD→DDR DMA 是另一项可行的冷启动优化，需要独立实现与验证。

依据：[整机 CPU/NPU/DDR 连接](../../AI加速器/npu/system/rtl/ag_npu_system.sv)、[矩阵 DMA](../../AI加速器/npu/system/rtl/npu_dma_top.sv)。

## 三、对《项目瓶颈与可用化路线》的评估

### 3.1 值得采纳的方向

- 权重预取、缓冲与计算重叠。
- 减少中间数据回写及重复读取。
- 减少 staging 复制、重复量化和小任务提交。
- 建立独立高精度参考并检查整图及真实任务质量。
- 分别报告 SD 冷启动和模型常驻 DDR 后的暖推理性能。

### 3.2 Delta q/k 缩放诊断不成立

文档混淆了 L2 归一化与 RMSNorm，不能采用其中将常数 `512/5793` 改为 `5793/65536` 的建议。

现有 float 路径为：

```text
q_out = q / sqrt(sum(q²) + ε) / sqrt(d)
k_out = k / sqrt(sum(k²) + ε)
```

而整数适配调用的是 RMSNorm。两者关系为：

```text
RMSNorm(x, ε/d)
  = x / sqrt(sum(x²)/d + ε/d)
  = sqrt(d) × x / sqrt(sum(x²) + ε)
```

因此，使用 RMSNorm 实现上述 float 公式，所需权重为：

| 输出 | RMSNorm 后的权重 | d=128 时的 Q16 常数 |
| --- | ---: | ---: |
| q：L2 归一化后再除以 sqrt(d) | 1/d | 512 |
| k：L2 归一化 | 1/sqrt(d) | 5793（舍入值） |

当前整数调用中的 `512` 和 `5793` 有数学依据；epsilon 从 Q32 的 `4295` 按维度转换并舍入为 `34`，也与这项转换相符。直接采用文档建议会改变递推计算。

这不代表当前定点精度已经足够。舍入、小幅度信号、递推状态格式等仍可能造成误差，但需要通过匹配数值策略的逐阶段对照定位，不能归因于上述常数“少乘 sqrt(128)”。

依据：[float Delta 公式](../../AI加速器/npu/system/integration/agent_runtime_20261101/sw/model/qw_math.c)、[整数模型适配](../../AI加速器/npu/system/integration/agent_runtime_20261101/sw/model/qw_tensor_v2.c)、[RMSNorm 数值实现](../../AI加速器/npu/system/sw/npu_tensor_reference.c)。

### 3.3 旧 profile 的 CPU 调度开销计算有误

对应冻结工程中，矩阵引擎及 busy 计数器运行在 CPU 的 81MHz 域，不是 DDR UI 的 125MHz 域。

| 指标 | 正确换算 |
| --- | ---: |
| 硬件 busy：408,577,718 周期 / 81MHz | 约 5.044 秒 |
| raw 总区间：410,170,663 周期 / 81MHz | 约 5.064 秒 |
| 两个区间的差额 | 约 0.020 秒 |

因此不能据此推导出“1.79 秒 CPU 提交、轮询和维护开销”。新整图路径每 token 的任务数量更多，调度开销仍值得优化；上述旧数据也不能反过来证明新路径调度开销很小。

依据：[旧板端 profile](../../NPU_HANDOFF.md#历史计时口径)、[对应冻结工程时钟连接](../../NPU_HANDOFF.md#历史计时口径)。

### 3.4 激活已经预加载到片上缓存

`npu_dma_top.sv` 已有 `activation_cache`。`ACT_FETCH` 读取本地缓存，并非每次重新向 DDR 取激活。

所以“增加激活驻片即可再去掉一半 DDR 流量”的判断不符合当前实现。激活本地读取和复用仍可优化，但应区分本地读周期与外部 DDR 流量。

### 3.5 提速倍数和吞吐量属于预算

“约30倍提速”“2.4～3.8 token/s”尚无当前整机实测支撑。64-lane 值得作为性能候选，但两行预取并不自动保证每周期供数；还取决于访存延迟、在途请求、归约、状态访问及调度成本。

16-lane 在 81MHz 下的理想算力不足以支持所列模型的 2 token/s，但“任何时钟下都不可能达到”这一说法过强。

多 token 权重复用可以节省带宽，不能消除计算本身的 MAC 下界。32-token prompt 在 64-lane、81MHz 下仅 body 的理想计算就约需3.07秒，因此不能仅靠权重复用保证 TTFT≤3秒。

### 3.6 当前 logits 差异的归因需要修正

现有 host 对照的基线为 W4 body＋BF16 head，候选为整数路径＋W4 head，并非对官方全 BF16 模型的比较。

当前约19.73%的 relative L2 同时受到整数计算和 head 精度策略变化等因素影响，不能直接将其全部归因于某一种定点格式，也不能据此测得相对于官方 BF16 body 的 W4 量化损失。

需要匹配 head 与权重策略的对照，以及独立高精度整模型参考。现有 `quality_approved=false` 应保持。

依据：[实际 host 对照程序](../../AI加速器/npu/system/sim/tensor_model_host.c)、[8-token 运行日志](evidence/model_result.json)、[结果](evidence/model_result.json)。

## 四、对《建议.md》的评估与 I/D Cache 现状

### 4.1 合理原则

- MMIO 不进入普通数据缓存。
- 非一致性 DMA 前后显式维护缓存。
- 关键代码、栈和调度路径合理使用 TCM。
- 仲裁同时考虑 NPU 吞吐和 CPU/交互响应，避免长期饥饿。

### 4.2 当前已经具备的能力

**I/D Cache 已实现并在板级配置中启用，不需要从零建设。**

| 项目 | 当前实现 |
| --- | --- |
| 组织 | 独立的两路组相联 I Cache、D Cache |
| 板级容量 | I 16KiB＋D 16KiB |
| 行大小 | 32B，与256-bit DDR单拍匹配 |
| 数据策略 | 写回、写分配 |
| TCM、MMIO | 旁路 |
| DMA 一致性 | 软件显式维护，不具备硬件自动一致性 |
| 范围维护 | 已实现按范围 clean＋invalidate，保留全 Cache 回退 |

已有真实 RV32＋Cache＋矩阵/tensor DMA 的集中验证报告。CPU 独立 Cache 工程也有历史时序闭合和板测归档，但这些结果不能替代最新 CPU＋NPU 整机的验收。

依据：[板级开关](../../fpga/board/ag_ddr_board_top.sv)、[Cache 设计与历史证据](../../docs/两路Cache设计与性能.md)、[范围维护说明](../../NPU_HANDOFF.md#cache与dma一致性)、[四事务整机仿真报告](evidence/cpu_queue4.json)。

### 4.3 不能直接采用的建议

- `0xC0000000` 目前不是已实现的 DDR 非缓存别名。增加这种别名需要地址译码、物理映射和缓存旁路逻辑；`volatile` 不会关闭硬件缓存，不能称为“零硬件改动”。
- 将 DDR 最后128MiB直接划给 CPU，会与现有接近满容量的模型内存布局冲突，需要重新规划。
- 当前 DDR UI 是125MHz，不能直接按文档的133.25MHz估算。
- 现有32B行已匹配DDR单拍；64B行不一定更快，需要评估随机访问、额外填充和资源成本。
- 当前四事务队列不等于已实现长 burst 或权重连续预取。
- CPU 上 Top-P、重复惩罚、sin/cos 或分词的具体性能需要实测，不能承诺“几毫秒”或“质量提升一档”。采样策略也不能替代数值正确性验证。

## 五、时间紧情况下的建议实施顺序

### 1. 闭合最新整机的 I/D Cache 功能和一致性

保持 I/D Cache 启用，确认实际 Agent 固件使用正确驱动，集中验证：

- CPU 脏数据发布后，NPU 能读到正确输入。
- NPU 写回后，CPU 获取正确输出。
- CPU 与 NPU 并发时，事务归属和响应正确。
- 错误、超时及恢复过程中，不错误发布或复用数据。
- 记录命中、未命中、写回和维护成本，确认 Cache 在真实应用中的收益。

这里的“闭合”先指功能、配置和一致性闭合；最新整机物理时序随后集中处理。

### 2. 优先优化矩阵供数

保留原基线，使用明确的64-lane性能配置，完成权重预取、缓冲及计算重叠，再评估融合归约，减少 partial 往返DDR。

以整机周期、DDR事务和数值对照评估收益，不仅检查单个计算核。

### 3. 减少每 token 的软件开销

复用 body 公共激活量化，减少 staging 复制、小任务提交和重复缓存扫描。跨算子常驻数据需要明确所有权和发布边界，不能简单删除缓存维护。

### 4. 集中整图验收，再处理最终时序和板测

减少不必要的中间小测试，将验证集中在真实整图、Cache/DMA协同和明确的故障路径。性能修改同步检查数值变化与工具任务质量，最后完成同源时序、位流和板端持续吞吐量验收。

SD冷启动单列处理，避免与暖推理吞吐混报，也避免分散当前性能优化精力。

## 六、结论

当前最值得投入的是现有 DMA 的供数效率、跨算子数据复用，以及 Cache 一致性开销。NPU 直接访问 DDR 与 I/D Cache 都已经具备基础实现，后续应在最新整机上完成集成和验证。

第一份文档提出的 Delta 缩放修改应明确排除。最新整图质量尚未批准，实际板端吞吐量仍缺证据；二者最终必须一起验收。
