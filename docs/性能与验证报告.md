更新：2026-10-29。当前 **AG 从现有源码重新实现的 102 MHz TCM SoC 已通过实板 CoreMark、JTAG 配置回读与实板 ILA**。6000 轮 / 1,189,859,177 周期，11.665286 秒，514.346581 CoreMark，5.042613543 CoreMark/MHz；同一布线工程 7023 LUT，0.073237446 CoreMark/LUT。最终 setup +0.156 ns，All Constraints Met。

独立 ILA 版本 7655 LUT / 3755 FF / 52 DRM36K，102 MHz setup +0.313 ns，6000 轮周期与 CRC 不变，配置回读通过。65 位 ×2048 点真实 JTAG 立即捕获覆盖链表与 CRC 循环，窗口退休 2286 条，IPC 1.116210938，477 周期双退休，239 周期无退休。该局部窗口不能替代全程 IPC，未探测的气泡原因不作猜测。源代码/固件/时序/资源/串口/原始 WDF/全部 CSV 样点与复现命令在[本次 AG 归档](results/ag-contest-20261029/README.md)。

保留旁路比较预寄存、异常信息按指令类提前选择、除法器空闲操作数捕获，并用 PDS 路由迭代完成闭合。随后尝试的位计数树和乘法完成预译码虽通过功能验证，但本轮布局结果未超过已闭合版本，已留在 `build/experiments/counttree-*.sv`，未作为发布 RTL。独立位计数测试保留在 `sim/alu_bitcount_tb.sv`。

源文件重建 SHA-256 与闭合工程一致：`C64939B547155FD2BDEEE073AE965307A51874878B7877FA72B0CFBAFDB5C37F`。证据见 `docs/results/offline-102mhz/`。PDS 报告的估计 Fmax 103.2642 MHz 不是另一个已经配置、闭合或上板的频点。

## 2. 测试和统计口径

- 自主六级顺序双发射 RV32IM + Zicsr/Zifencei + Zba/Zbb，动态通道交换、四项指令队列、256 项 BTB、3 位局部历史、16 项 RAS、early LSU 与 Load 旁路。
- 64 KiB TCM、UART TX、GPIO、mtime 和软件中断。本节基准配置不含 Cache、DDR、OS 或 AI 加速器；新 DDR 集成工程另行统计。
- GCC 13.2.0，`-march=rv32im_zicsr_zifencei_zba_zbb -mabi=ilp32 -O3 -funroll-all-loops -finline-limit=1000 -frename-registers -mtune=sifive-7-series`。完整参数见 UART 日志。mtune 只影响编译调度，未使用第三方 CPU 核。
- 上游 CoreMark 提交 `1f483d5b8316753a742cbf5590caf5bd0a4e4777`，算法文件未修改，2000 字节、单上下文、performance 种子。list / matrix / state CRC 为 `e714 / 1fd7 / 8e3a`。
- 使用完整 64 位 mcycle 计时，不包含启动和随后打印。上游整数秒数会截断；108 MHz 日志中的 Iterations/Sec=571，应按完整周期换算为 **544.602348**。
- LUT 取同一位流的 Place & Route 层次汇总，包括 CPU、TCM 周边逻辑及最小外设。不能混用 Device Map、综合或芯片总容量；Distributed RAM LUT 已包含在 LUT 内，不能重复相加。

```text
CoreMark/MHz = iterations × 1,000,000 / measured_cycles
CoreMark = iterations × clock_hz / measured_cycles
CoreMark/LUT = CoreMark / implemented_luts
```

这些是本工程测试结果，未做 EEMBC 认证。27 MHz 启动和早期架构比较保留在[上板调试记录](上板调试记录.md)、[历史性能报告](历史性能报告.md)。

## 3. 面积效率评估

赛题 PDF 印刷页 9 同时评估 CoreMark/MHz、满足约束的频率和 CoreMark/LUT，未给出统一及格阈值。当前执行效率超过 5，但面积效率仍是短板。

| 108 MHz 位流资源 | LUT | 占全 SoC |
| --- | ---: | ---: |
| 整个 CPU | 6809 | 95.6% |
| 其中：预测器 | 1445 | 20.3% |
| 其中：两个 ALU | 863 | 12.1% |
| 其中：CSR | 547 | 7.7% |
| 其中：两路译码与预译码 | 487 | 6.8% |
| 其中：除法器 | 200 | 2.8% |
| CPU 之外全部逻辑 | 315 | 4.4% |

子模块包含在 CPU 汇总中，不能重复相加。面积偏大主要在 CPU 内部，不能归因于 UART、PLL 或尚未接入的 DDR。仅统计 CPU 也只有 544.602348 / 6809 ≈ **0.079983 CoreMark/LUT**。

[VexRiscv 官方 README](https://github.com/SpinalHDL/VexRiscv#area-usage-and-maximal-frequency) 的 full max perf 配置列出 Artix-7 上 2.57 CoreMark/MHz、200 MHz、1935 LUT，换算约 0.266。它使用不同 FPGA、工具和核级统计边界，不能用于同平台排名，但说明高 CoreMark/MHz 不自动等于高资源效率。

下一阶段首先以**时序闭合且 CoreMark/LUT ≥0.10**为优化目标，而非已实现指标。例如 100 MHz、5 CoreMark/MHz、5000 LUT 对应 0.10；按 108 MHz 当前吞吐，则需不超过约 5446 LUT。优先评估旁路/发射/队列控制和预测器读写结构，比较面积降低与误预测、停顿成本。保留双发射的同时，应以完整实现结果判断收益，不能通过隐藏资源、修改基准算法或放宽真实时序路径提高数字。

## 4. 本轮修改和验证

最终保留：独立左/右移位通路，去掉共享移位器两端的方向选择；除法器直接捕获原始操作数，除零与有符号溢出经过迭代，结束处得到规范结果，去掉输入宽比较使能链。普通除法和 CoreMark 短测周期未变化；除零及有符号溢出完成延迟增加。

最终 RTL 通过 smoke、70 项指令、15 类异常/CSR、机器态中断、19 组双发射、219 轮随机等待差分（102240 条退休指令，20849 条第二通道退休）、UART 单元和 SoC 波形检查。短 CoreMark 为 5.041916 等效 CoreMark/MHz、算法 CRC 正确；因不足 10 秒，短测不作为正式成绩。根目录 PDS 工程已同步，重新 Compile 通过。

MMIO 请求分级和并行旁路选择没有改善最终时序，已撤回，实验源码与日志保留在 build。该历史版本的原始 RTL 重建合并文件与已测 108 MHz 源文件的 SHA-256 完全相同：`33D1ADADCF736CF159FF3D7810EC23615F2896B6FDB5D7FAF9364E8B0B8FF955`。

一次附加 RTL 长测的上限误设为 15 亿周期，但实际加载的 8000 次固件需超过 15.86 亿周期，因此在预算处停止；该运行不计为通过，也不据此认定算法错误。108 MHz 成绩直接来自两次完整实板测试。

## 5. 上板复现

PowerShell，在工程根目录运行。COM12 为本机 CP210x UART，115200 baud、8N1；换插口后需核对实际端口。

```powershell
# 已闭合的 81 MHz 归档镜像
.\scripts\program_board.ps1 -Port COM12 -Profile build\board81-coremark `
  -Output build\board81-repeat.uart.log `
  -Expected 'MEASURED_CYCLES_HEX=[0-9a-fA-F]{16}\r?\n'

# 108 MHz 实验镜像：显式允许尚未闭合的 setup 时序
.\scripts\program_board.ps1 -Port COM12 -Profile build\board108-shiftdiv `
  -Output build\board108-repeat.uart.log -ExperimentalTiming `
  -Expected 'MEASURED_CYCLES_HEX=[0-9a-fA-F]{16}\r?\n'
python scripts\analyze_board_coremark.py build\board108-repeat.uart.log --clock-hz 108000000 --luts 7124
```

默认下载仍要求时序通过。实验模式额外核对时序报告哈希，并要求慢角和快角 hold 均通过，不会把 manifest 的 routed_timing_passed 改成 true。串口在下载前打开，取得完整结果后才进行配置回读校验，避免回读影响软件运行。
