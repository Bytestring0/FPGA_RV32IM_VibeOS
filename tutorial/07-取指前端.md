# 7. 写取指前端：把内存返回的两条指令排进队列

先想象一次延迟取指：CPU 在地址 `0x100` 发出请求，内存三拍后才返回。等待期间，下一次希望取的地址可能已经变了；甚至分支已经证明 `0x100` 所在路径是错误的。响应回来时，我们怎么知道它属于哪个 PC，又怎么防止错误路径指令进入执行？

这个问题不能靠“有一个 PC 寄存器”解决。本章把项目的取指前端分成三个独立职责：

1. `f_pc`：下一次希望请求哪个地址。
2. `q_*`：已经接收的那笔请求是什么、它后来有没有被作废。
3. `fetch_*`：已经返回、等待发射的指令队列。

对应源码从 [状态声明](../rtl/rv32_core.sv#L50-L83)、[请求/响应控制](../rtl/rv32_core.sv#L455-L463) 到 [时钟沿更新](../rtl/rv32_core.sv#L522-L578)。请边阅读边画时序。

## 7.1 先从最保守的实现开始

不考虑预测和双发射，一个最简单的前端：

```text
空闲：给出 PC 和请求 valid。
请求被接收：保存请求 PC，进入等待。
响应被接收：将指令、保存的 PC 和错误位放进一个寄存器。
后端接收：释放该寄存器，继续取下一条。
```

如果总线响应至少下一拍才来，保存 PC 就很自然：时钟沿 A 接收请求，时钟沿 B 或更晚接收响应。即使 A 之后更新了下一 PC，也不会丢失本次请求的地址。

这里假定后端没有同时发出重定向。加上分支后，已接受请求不能凭空消失，内存还可能按原契约返回响应。必须把它标记作废，并在返回时消费但不加入队列。

## 7.2 为什么返回 64 位

项目的接口一次从请求地址返回两条可能连续的 32 位指令：

```text
q_pc                → i_rsp_data[31:0]，错误位 i_rsp_error[0]
q_pc + 4            → i_rsp_data[63:32]，错误位 i_rsp_error[1]
```

这样前端一次响应最多可给双发射提供两条指令。注意请求地址由 `f_pc` 给出，并不是要求把 PC 强制对齐到 8 字节；第二条是 PC+4。SoC 的 TCM 使用同步读取两个相邻字，末尾地址可能使第二个字报错。这个错误位要与其指令分别保存，不能把第一个字的成功当成第二个字也成功。

如果预测第一条的下一 PC 不是 PC+4，就不应该把 PC+4 的指令当作预测路径的第二项；因此有 `q_has_second`。它与是否真的双发射不是同一件事：两条都在队列里时，后端仍可能因为依赖、类型或错误而只发射一条。

## 7.3 哪些东西必须跟着请求保存

代码中的一笔在途取指上下文包括：

```systemverilog
logic q_valid, q_killed;
logic [31:0] q_pc, q_pred, q_pred_second;
logic q_has_second;
```

请求被接收时保存：

```text
q_pc          本次请求第一个指令的地址
q_pred        对第一个指令预测的下一 PC
q_pred_second 对第二个指令预测的下一 PC
q_has_second  是否接收第二个字作为队列项
q_killed      该请求是否已被重定向作废
```

为什么连预测也要保存？EX 执行一条分支时，要将**当初对这条指令做出的预测**与真实下一 PC 比较。如果等它执行时才读取预测器当前输出，预测器早已在看别的 PC，更新状态也可能变化，比较对象就错了。

## 7.4 阅读请求与响应的握手条件

项目使用：

```systemverilog
assign i_rsp_ready = q_valid && (q_killed || fetch_redirect ||
                     fetch_count <= (q_has_second ? 3'd2 : 3'd3)) && !rst;
assign i_consume = i_rsp_valid && i_rsp_ready;
assign i_req_valid = (!q_valid || i_consume) && !fetch_redirect && !rst;
assign i_req_addr = f_pc;
assign i_accept = i_req_valid && i_req_ready;
```

逐项解释：

- 没有有效的 `q_valid` 时，不能把任意响应认作自己的事务。
- 两条都需要入队时，当前队列最多有 2 项，才能保证有 2 个空位；只需一条时最多 3 项。
- `q_killed` 或已登记的 `fetch_redirect` 表示响应不再需要进队列，可以消费它以清掉旧事务，即使队列空间不足。
- 同一沿消费旧响应时，可以接受新请求：`!q_valid || i_consume`。这是吞吐优化，状态更新必须定义同拍优先级。
- `fetch_redirect` 生效时暂不发新请求；复位期间也不发。

队列空间判断使用当前 `fetch_count`，不是依赖同拍将发射多少条来冒险腾空间；这可能保守一点，却避免把后端晚到的发射/暂停条件串进关键路径。

## 7.5 把同拍响应和新请求放进时序表

假设 `q_valid=1` 对应旧请求 A，当前响应 A 有效、队列有空间，同时新的请求 B 被接受：

| 时钟沿前 | `i_consume` | `i_accept` | 时钟沿后 |
| --- | ---: | ---: | --- |
| A 响应到达，B 可接收 | 1 | 1 | A 的指令入队，`q_*` 保存 B，`q_valid=1` |
| B 尚未返回 | 0 | 0 | 保持 B 的上下文 |

看 [533–540 行](../rtl/rv32_core.sv#L533-L540)：先写 `if (i_consume) q_valid <= 0;`，后写 `if (i_accept) q_valid <= 1;`。在同一个时序块里，两次非阻塞赋值给同一个变量时后面的赋值优先，所以这个特定代码结构确保同拍新请求覆盖旧状态。维护者如果把两个独立 if 改写，必须重新验证这一时序，而不是只看单独两个分支。

不要在你的实现中依赖多个分散 always 块同时驱动同一寄存器；那会引入多驱动或不确定优先级。

## 7.6 已在途请求碰到重定向

假设地址 0x100 的请求已经接收，但尚未回应。此时较老的分支在 EX 决定跳到 0x200：

```text
沿 1：请求 0x100 被接受，q_valid=1、q_pc=0x100。
沿 2：分支判定需要重定向；当前取指队列清空，旧请求标记 killed。
沿 3 或以后：内存返回 0x100 的数据；响应握手后丢弃，不入队。
前端从重定向目标继续请求；具体重叠时机由接口/当前状态决定。
```

项目用 `redirect`、一个寄存后的 `fetch_redirect` 以及 `front_flush` 协调，见 [449–461 行](../rtl/rv32_core.sv#L449-L461) 和 [524–578 行](../rtl/rv32_core.sv#L524-L578)。这样把晚到的重定向使能与取指 PC 更新拆开，有助于时序。不要仅在看到重定向时把 `q_valid` 清零：旧响应将无法配对，而且新旧请求可能混淆。

还有一个竞态：本周期产生重定向时，旧请求可能被消费，新请求也可能被接受；项目给新上下文设置 `q_killed <= redirect`，确保错误路径的新响应未来被丢掉。请按真实信号画出 `redirect`、`fetch_redirect`、`i_accept` 三者跨拍关系，而不是把它们合并成一个直觉上的“跳转时刻”。

## 7.7 队列每项要携带哪些字段

项目每项保存：

```text
fetch_pc[i]     指令的 PC
fetch_insn[i]   指令本身
fetch_pred[i]   该指令当时预测的下一 PC
fetch_error[i]  对应的取指错误
fetch_meta[i]   预译码后发射所需的少量元数据
```

`fetch_count` 从 0 到 4。队首 index 0 是较老的候选，index 1 是可能配对的相邻年轻候选。指令与其 PC/预测/错误/元数据必须一起移动；如果只移动 `fetch_insn` 而漏掉 `fetch_error`，异常可能被归到另一条指令。

预译码不代替完整译码：它提前保存 `illegal/serial/branch/reg_write/use_rs*` 和“是否可在简单 ALU 执行”等少量信息，让队列与发射决策不必等待完整译码的输出多路选择。完整译码器仍对队首两条产生 `id_dec` 和 `id_dec_second`。

## 7.8 同一拍出队和入队怎么写

假设沿前队列为：

```text
[A, B, C]，fetch_count=3
```

后端发射 A 和 B（`fetch_pop=2`），同拍响应带回 D 和 E：

```text
先概念性出队：[C]
再概念性追加：[C, D, E]
新 fetch_count=3
```

对应索引：旧 index 2 的 C 搬到新 index 0；D 写 index 1；E 写 index 2。若只发射 A，则应是 `[B,C,D,E]`；若队列没有空间容纳本次响应，不应握手响应。

项目用 `fetch_remaining = fetch_count - fetch_pop` 表示发射后的数量，用组合比较把新条目写入对应数组位置；每个字段各自赋值。因为同一时钟沿对某个数组元素的压缩写与追加写可能同时成立，源码后写的追加赋值应当成为该位置的最终值，不能随意调整语句顺序。

**注意区别抽象模型和当前 ready 条件**：上面 `[A,B,C]` 同拍出 2、入 2 是一个队列行为练习；项目当前 `i_rsp_ready` 对两条响应要求沿前 `fetch_count<=2`，因此在 count=3 时不会接收该双字响应，即使同拍计划弹出两条。该设计有意使用保守预留。用更复杂的前视空间计算优化它时，必须考虑组合路径和循环依赖，并写专门测试。

`front_flush` 最终令 `fetch_count<=0`。即使同一沿数组数据被写入或压缩，只要 count 为 0，旧载荷就不可见；valid/count 是真实性依据，不能仅凭数组内仍有旧字就认为其有效。

## 7.9 实现自己的版本：按这个顺序来

1. 只做单次请求，保存 PC；用 testbench 让响应延迟 1、2、7 拍，检查每条指令的 PC 对应正确。
2. 实现一个一项指令缓冲，后端不 ready 时保持指令和 PC。
3. 换成四项队列，只允许一次弹出/插入一项；穷举空、满、中间状态。
4. 加第二条返回值和 `q_has_second`，分别检查两个错误位与 PC。
5. 加同拍出入；构造所有合法 count/pop/push 组合，检查新数组和 count。先用保守 ready，确认不会溢出。
6. 加重定向和 killed：等待中、响应同拍、新请求同拍均要测；错误路径的指令绝不能退休或写内存。
7. 最后保存预测结果，后端拿真实下一 PC 比较。预测器尚未实现时，用顺序 PC 作为预测。

建议先做一个简洁、易证正确的队列模型，再与项目的提前比较及紧缩写法对照。自己设计时可以用临时 next 数组明确表达“先 pop 再 push”，但应验证目标 FPGA 工具是否能综合推断你想要的结构。教程提供了一个可运行的 [四项队列实验](16-核心组装施工手册.md#167-第六个里程碑写前端队列并单发射)，用随机出入和 flush 对照软件队列；它只是队列，不实现完整取指前端。

## 7.10 如何验证，而不是只盯着 count

测试台为每条指令附唯一 PC 和不同错误位，记录所有**接收到且未被 kill**的条目；按后端握手顺序检查队首输出。并加入：

- 先请求后等待 0 个额外等待周期或多个周期；项目契约下响应最早是接受后的下一周期。
- 后端停住，队列满时响应必须保持而不能被覆盖。
- 重定向恰与响应握手同拍；旧路径不得成为有效输出。
- 第一字成功、第二字错误；第一个预测转移时第二字不得被误用。
- 连续两组响应，检查第一个响应的 PC 没有被第二个请求的 PC 覆盖。
- 请求已接受后发生 flush，旧响应在很久后到达并被丢弃。

把取得的指令送入流水线之后，另一个问题随之出现：数据尚未准备好的指令如何停止，而后面的指令如何不越过去？继续 [第 8 章](08-单发射流水线.md)。
