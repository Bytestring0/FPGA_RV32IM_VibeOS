# 15. 从仿真走到 FPGA：赛题、时序和证据

前面我们一直在回答“电路应该做什么”。上板还要回答“这个电路有没有被正确映射到目标 FPGA、以多少真实频率运行、引脚和固件是不是同一个版本”。如果只把 PDS 约束写成 110 MHz，就宣布 CPU 以 110 MHz 通过比赛，属于把目标当成测量结果。

本章先逐条对照赛题，再解释 PDS 工程、上板操作与 CoreMark 计算。赛题依据是 [紫光.pdf](../紫光.pdf) 的 PDF 第 10–11 页（印刷页 8–9）；主办方后续通知或勘误若与该版本不同，应以最新正式文件为准。

## 15.1 题目要求与当前项目有什么差距

| 题目要求 | 项目目前可查证的状态 | 下一步 |
| --- | --- | --- |
| 基础 RV32I | 项目声明支持并有 ISA/定向测试 | 按当前源码与赛题要求复现，记录覆盖与跳过项 |
| 至少三级流水线、处理数据冲突和分支 | 六级顺序流水线，含旁路、暂停、重定向 | 用测试与波形展示依赖和错误路径行为 |
| UART、GPIO 等基础外设 | 最小 SoC 有 UART TX、GPIO、计时器 | 核对实际板卡、引脚和输出，不把 TX 当完整 UART 收发 |
| 两路组相联指令/数据 Cache，优化突发 | **默认项目未实现 Cache** | 单独设计 I/D Cache、总线、替换、填充与一致性，验证再上板 |
| 动态分支预测及完整异常/中断 | 有动态预测和 M-mode 异常/中断 | 说明实现范围，向主办方确认“完整”的特权范围 |
| AI 加速单元、YOLO 或轻量大模型、传感器/显示应用 | **没有完整端到端 AI 应用** | 集成算子、软件栈、模型、数据输入输出并测精度/延迟/资源 |
| CoreMark/MHz、时序闭合最高频率、CoreMark/LUT | 有历史 TCM 配置板测报告 | 用同一版本的位流/固件/频率/时序/资源留证 |
| 性能分析与 ILA 波形 | 有设计和性能报告 | 按正式要求采集并解释真实 ILA 波形；不能用仿真波形冒充 |

题目要求 CoreMark v1.0 运行不少于 10 秒，列出的软件工具链为 `riscv32-unknown-elf-gcc`。项目当前默认用 `riscv64-unknown-elf-gcc` 并指定 RV32/ILP32；是否接受该前缀及具体工具链版本，应提前问主办方。题目没有在所读页面列出各项权重或完整特权级范围，不应自行猜测。

## 15.2 根工程和板级工程不是同一个东西

根 [RiscV.pds](../RiscV.pds) 用 `qinglong_fpga_top` 和生成的 `fpga/generated/qinglong_all.sv`，适合 PDS 编译/综合与时序探索。根据项目说明，根工程使用 27 MHz 原始时钟，约束中的高频目标不会自动生成 PLL，而且根工程不包含完整板级引脚约束。

板级工程由 [prepare_board.ps1](../scripts/prepare_board.ps1) 生成，包含板卡时钟、复位、引脚约束和所选固件。27/81/96/102/108 MHz 是该脚本支持的配置，是否实际闭合和可用必须看对应构建的报告。

可选 DDR 板级工程是另一套生成路径，涉及 IP、桥和附加约束；请单独读 [DDR 接入说明](../docs/板载DDR3接入与验证.md)。DDR 本身不是两路组相联 Cache，也不能继承 TCM 位流的资源和性能结果。

## 15.3 为什么项目有合并的 SV 文件

PDS 2022.2 ADS 对跨文件 package/struct 端口有兼容限制。项目将 [rtl/files.f](../rtl/files.f) 中按依赖排序的 RTL 合并成一个编译单元，再加入顶层。日常开发应改 `rtl/` 原始文件，然后重新生成；不要只改生成文件，也不要同时向 PDS 加入合并文件与原始模块，否则可能出现重复定义。

同步主工程的脚本会覆盖生成源码、根目录 `firmware.hex` 和工程设置。请先备份并确认文件内容，再在**实验副本**中执行，具体命令与覆盖说明见 [PDS 使用说明](../docs/PDS使用说明.md)。

## 15.4 一个安全的上板顺序

以下是操作顺序，不代表本轮已经替你执行 PDS 或下载：

1. 在独立副本完成 `make check`；生成你要使用的 `build/smoke.hex`。
2. 确认开发板型号与器件、时钟源、复位极性、UART 电平和引脚；不要把其他板卡的约束套到本板。
3. 使用现有板级生成脚本生成**新的输出目录**，并检查其 manifest、合并源码、固件与 `board.fdc`。
4. 用 PDS 执行 Compile → Synthesize → Device Map → Place & Route → Report Timing；检查 setup、各约束相关的 hold、未约束路径和报告版本。
5. 所有目标约束满足后生成位流，记录位流、固件、RTL、约束、工具版本与哈希。
6. 按板卡操作手册连接 JTAG、电源和 USB-UART，确认串口实际 COM 口、115200 8N1；先抓串口再下载以免漏掉启动信息。
7. 验证下载/配置与串口输出，将板测日志与该位流 manifest 关联。断电启动和外部 Flash 固化是另外的测试，不可自动推断成功。

原始脚本默认使用项目 `build/board<频率>` 输出并可能覆盖该目录的生成文件。若要尝试，明确指定一个不存在的 `-OutputDirectory`，先检查脚本参数和目标路径：

```powershell
# 在独立项目副本根目录，先确认 build\my-board27 不存在且 firmware 已生成
.\scripts\prepare_board.ps1 -ClockMHz 27 -Firmware build\smoke.hex `
  -OutputDirectory build\my-board27 -Build -Bitstream
```

脚本默认 PDS 安装位置是本机配置；不同机器需要核对 `-PdsRoot`。`-Build` 会真实运行工具并写输出；在没有板卡、正确工具或权限时不应声称上板成功。具体 GUI/串口流程和注意事项见 [PDS 使用说明](../docs/PDS使用说明.md)、[上板调试记录](../docs/上板调试记录.md)。

## 15.5 看懂 setup 和 hold

时钟约束描述我们要求工具满足的时间，不会改变时钟硬件。若目标频率 100 MHz，则周期是 10 ns；如果布局布线后最差 setup slack 为 -0.5 ns，说明按该约束存在路径未满足，不能称这个构建在 100 MHz 时序闭合。

即使 setup 全部满足，也要检查 hold、生成时钟、跨时钟域、复位和 I/O 约束等；缺失约束造成“看起来全绿”同样不可靠。查看关键路径时标出起点/终点、组合逻辑和布线延迟，再决定是调整微架构还是降低时钟。时序报告中的估计 Fmax 不自动等同于已经配置、闭合且上板验证的频率。

## 15.6 CoreMark 三个量怎么计算

假定测得迭代次数 N、计时周期数 C、实际工作时钟频率 F（Hz），以及同一位流布局布线后的 LUT 数 L：

```text
运行秒数       = C / F
CoreMark       = N / (C / F) = N × F / C
CoreMark/MHz   = N × 1,000,000 / C
CoreMark/LUT   = CoreMark / L
```

如果打印出来的秒数取整，直接用 `N / 打印的整数秒数` 可能有显著误差；应使用完整周期计数与真实时钟。`CPU_HZ` 软件参数只影响换算，改它不会改变硬件时钟。计数区间要说明是否包含启动、打印等开销；CRC、编译选项、CoreMark 版本、迭代数和数据规模也要记录。

赛题要求的运行时间不少于 10 秒。短测即便 CRC 正确，也只用于功能/性能趋势检查，不是正式成绩。未经过 EEMBC 认证的结果应如实说明，不能称为官方认证分数。

## 15.7 如何正确使用仓库已有的数字

[性能与验证报告](../docs/性能与验证报告.md) 记载了一个历史的 102 MHz 最小 TCM 配置：6000 次迭代、1,189,859,177 周期，按标称 102 MHz 约 11.6653 秒，约 514.3466 CoreMark、5.0426 CoreMark/MHz；同一实现报告 7089 LUT，约 0.07256 CoreMark/LUT，setup WNS +0.120 ns，慢/快角 hold +0.059/+0.041 ns。

这些是**归档版本的历史证据**，不是本次教程重写新做的板测。报告也明确说后续 RTL 或 DDR 修改会改变源码哈希，不能直接继承旧位流成绩；108 MHz 历史实验 setup 未闭合，不能作为满足约束的最高频率。请以归档的 manifest、固件、源、约束与报告逐一核对，频率为配置的标称 PLL 值，未用外部频率计校准。

## 15.8 如果要补赛题 Cache，先设计什么

这是**后续设计任务**，不是项目现状。以两路组相联 I-Cache 为例，先确定总容量、每行字节数、组数以及地址拆分：

```text
字节地址 = tag | set index | line offset
每组有两路：每路保存 valid、tag 和一条 cache line
```

命中时用 set 找到两路，比较 valid/tag，选中数据；未命中时选择无效路或替换路、向下级申请整行并等待返回，填充后再响应 CPU。设计时要明确：一次只能有多少缺失在途、下级 burst 的接受/错误/部分返回如何处理、flush/FENCE.I 怎样使旧指令不可见。

D-Cache 还需确定写直达或写回、脏位与逐出、字节写、MMIO 绕过、一致性及错误响应；DMA/AI 加速器读写内存时尤其不能默认自动一致。先做独立 testbench 覆盖冲突替换、边界、背压、错误与自修改代码，再接入 CPU 并复跑全套回归。赛题要求的突发优化必须在真实下级协议上实现并测量，不能把“每次发多个单字请求”直接宣称为总线突发。

## 15.9 AI 任务要证明整条链路

加一个乘加单元并不等于完成题目中的边缘 AI 系统。至少需要说明模型来源与许可证、量化/精度、算子覆盖、内存容量和数据搬运、CPU 调度与加速器接口、输入传感器或图像来源、输出显示/控制，以及端到端延迟和识别结果。资源和主频要按包含加速器的同一个实际位流统计，不能沿用只有 TCM CPU 的 LUT 数字。

具体模型、外设和开发范围应由团队与赛题规则共同确定；项目已有 [模型加速器整合方案](../docs/模型加速器整合与浏览器方案.md)，需核对哪些是已实现、哪些仍是方案。
