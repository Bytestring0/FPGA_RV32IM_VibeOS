# 20. 逐拍走读真实核心：把教学流水线扩成青龙

在第 19 章，你已经运行过一个单发射流水核心。这章不再重新画一个抽象 CPU，而是拿本项目 [rv32_core.sv](../rtl/rv32_core.sv) 的实际控制式和时序赋值，按“如果我要自己把这一块接出来，应当先写什么、一个时钟沿会发生什么、出错会看到什么”的顺序走读。

本章的目的是帮助你**动手实现并核对**，不是说复制零散片段就能得到完整核心。片段依赖项目的其余声明、模块和优先级。尤其注意时序块中同一变量多处非阻塞赋值时，沿后取最后执行的赋值；所有右侧计算仍来自沿前状态。

## 20.1 一次时钟沿涉及哪些事

从年龄由老到年轻，看一个普通沿可能发生的事情：

```text
WB：旧组退休，结果写入寄存器银行。
MEM：旧组若完成，将结果送入 WB；或者等待外部响应。
EX：若 MEM 可接收，执行组进入 MEM；分支可能请求重定向。
ID：若 EX 可接收、依赖/串行等条件允许，从队首发射 1 或 2 条。
前端：接受或丢弃取指响应，队列同时出队与入队，可能接受新请求。
```

这五行描述的是**同一个边沿之前算出的事件**，不是五段程序按顺序软件执行。写 `m_pc <= x_pc` 和 `w_pc <= m_pc` 时，WB 拿旧 MEM 的 PC，MEM 拿旧 EX 的 PC。

你可以先在纸上画一张表，横向是沿前状态，纵向是输出下一状态：

| 沿前观察 | 可能造成的沿后变化 |
| --- | --- |
| `w_valid` | 写相应寄存器银行；本拍对外报告退休 |
| `m_finish` | 将 MEM 结果/异常送往退休或 trap 逻辑 |
| `m_ready` 和 `x_go` | MEM 腾出空间并接收 EX，或变成空槽 |
| `x_ready` 和 `id_issue` | EX 接收队首，或变成空槽 |
| `i_accept` | 保存请求 PC 与预测上下文 |
| `i_consume` | 接收旧响应，可能向队列追加指令 |
| `front_flush` | 队列最终清空，旧路径请求被 kill |

具体优先级以源代码为准。这样画表最大的好处是避免一句“流水线向前移动”掩盖等待、同时替换和错误处理。

## 20.2 建寄存器组前先定义不变量

每组状态写一个最小不变量：

```text
q_valid=1 → q_pc/q_pred 等属于当前唯一在途取指。
fetch_count=N → 只有 fetch[0..N-1] 可作为指令使用，且按程序路径顺序排列。
x_valid=1 → x_pc/x_insn/x_dec/操作数属于物理主通道当前指令。
x_second_valid=1 → 辅助通道当前有另一条与主通道同组的指令。
m_valid=1 → MEM 的主通道载荷有效；m_sent 记录访存是否已经接收。
w_valid=1 → 第一个程序顺序退休口有效。
w_second_valid=1 → 第二个程序顺序退休口有效。
```

注意最后两项和 EX 不一样：EX 的主/辅助是物理通道，WB 对外第一/第二是**程序年龄顺序**。交换发射使两者不总相同，因此必须带 `x_swapped/m_swapped`。

要验证不变量，可以在仿真中打印 valid 与相应 PC/指令，检查 invalid 时不要根据旧 payload 下结论；也可以在自己的实现中加入断言，例如队列计数不得超过 4、辅助有效不得脱离同一组的主通道。任何断言都要先确认项目合法的异常边界，不能凭习惯把合法行为断言成错误。

## 20.3 先看双银行寄存器堆

项目使用两个单写银行和每寄存器最新银行标志：

```systemverilog
logic [31:0] regs_lane0 [0:31], regs_lane1 [0:31];
logic [31:0] regs_latest;
```

WB 第一退休口写 lane0、第二退休口写 lane1，同时设置该 rd 的 latest。读函数优先处理：

1. 若 index 是 0，返回 0。
2. 若当前第二退休口命中，返回第二结果。
3. 若当前第一退休口命中，返回第一结果。
4. 否则根据 `regs_latest[index]` 从相应银行读。

看 [read_operand](../rtl/rv32_core.sv#L201-L208) 和 [写入](../rtl/rv32_core.sv#L516-L521)。WB 直通是为了同拍发射读到尚未在数组中可见的新值。

自己实现时先写一个仿真表：

```text
沿前 x5 最新银行为 0、值 10。
这一拍第一退休口准备写 x5=20。
ID 也要读 x5。
read_operand 必须返回 20，而不是等待时钟沿后才返回 20。
```

同组 WAW 通常被禁止配对；即便如此，读口仍按代码明确第二口优先，不要凭“应该不会发生”把优先级写成工具相关。x1–x31 未要求复位，固件负责初始化必要状态；不要写测试假设它们均为 0。

## 20.4 从取指地址到接受事件

本项目的取指有两层 PC：

```text
f_pc：准备下一次发出的地址。
q_pc：已经被内存接受、正在等待响应的那次地址。
```

项目允许同一沿旧响应被消费、新请求被接受：

```systemverilog
assign i_consume = i_rsp_valid && i_rsp_ready;
assign i_req_valid = (!q_valid || i_consume) && !fetch_redirect && !rst;
assign i_accept = i_req_valid && i_req_ready;
```

这比第 19 章更积极：旧 `q_valid` 已为 1 时，如果旧响应在本沿消费，仍可发新的请求。写下一状态时，`i_consume` 首先让 q 清空，后面的 `i_accept` 再把新上下文装进去；两个事件都发生时，沿后 `q_valid` 应为 1，保存的是**新请求**。

一种测试方法：在响应返回那拍让请求 ready 保持 1，记录两个握手的 PC；下一次返回时必须仍与第二次请求的 PC 对应。故意把时序赋值顺序颠倒，再跑测试，通常会看到新请求的 `q_valid` 被错误清除。

## 20.5 为什么 `q_has_second` 要跟请求一起保存

64 位响应最多包括两条指令，但是否使用第二条由请求当时的预测/双发射配置决定。项目接收时记录：

```systemverilog
q_pred <= PREDICT_ENABLE ? prediction : f_pc + 32'd4;
q_pred_second <= PREDICT_ENABLE ? prediction_second : f_pc + 32'd8;
q_has_second <= DUAL_ISSUE &&
                (!PREDICT_ENABLE || prediction == f_pc + 32'd4);
```

第一条如果已经预测跳转，就不能无条件把顺序地址 `PC+4` 的第二条也当作同一路径；不开预测时，双发射可以接收顺序第二条。请求等待期间预测器状态和 `f_pc` 可能改变，所以应使用保存的 q 信息解释响应，不能重新查询“当前预测”。

写测试时把第一指令预测为顺序与预测为跳转分成两例，延迟响应后观察入队数量；再单独验证第二字错误位与第二条 PC 绑定。项目的真正行为还受前端 flush 和预测器实现影响，应结合 [实际控制](../rtl/rv32_core.sv#L524-L578) 对照。

## 20.6 队列如何为一次响应预留空间

项目不是只看“队列不满”，而是根据响应可能带一条还是两条判断：

```systemverilog
assign i_rsp_ready = q_valid && (q_killed || fetch_redirect ||
                    fetch_count <= (q_has_second ? 3'd2 : 3'd3)) && !rst;
```

`q_has_second=1` 时沿前队列最多两项才接收；仅一条时最多三项。这个判断保守地基于沿前 count，不依赖同拍 EX 是否能消费，减少一条跨级 ready 组合路径。

如果响应已被 kill，或者已进入 `fetch_redirect` 的清理周期，接收它是为了丢弃，而不是占队列；因此不需按正常入队预留空间。

试着手算：

```text
count=3，响应含两条：不 ready，即使这一拍预计弹出两条。
count=2，响应含两条：ready；若同时弹出一条，沿后 count=3。
count=4，q_killed=1：可 ready 接收并丢掉响应，不追加新指令。
```

这些是信号条件的例子；完整同时发生场景还需考虑 flush。教程的 [队列独立实验](examples/08-fetch-queue/fetch_queue.sv) 可以先练习出入队，但不实现本段 q 协议。

## 20.7 自己实现队列压缩和追加

设沿前队列为 `[A,B,C]`，`fetch_count=3`，本拍发射两条，响应返回 `[D,E]`。概念操作是：

```text
弹出 A、B → 保留 [C]
追加 D、E → 得到 [C,D,E]
新 count = 3 - 2 + 2 = 3
```

项目先形成 `fetch_remaining=fetch_count-fetch_pop`，每项按 pop=1 或 pop=2 移位；然后以并行相等比较，找到本次响应应覆盖的位置。查看 [541–578 行](../rtl/rv32_core.sv#L541-L578)：

- 每次移动时，PC、机器码、预测值、错误位和 metadata 一起移动。
- 第一响应字追加在 `fetch_count-fetch_pop`。
- 第二响应字若有效，追加在下一位置。
- `front_flush` 最终把 `fetch_count` 设为 0。

最后一条非常关键：数据数组本拍即便接受了旧路径 payload，只要最终 count 为 0，旧数据不可见。这样实现可以避免把较晚的分支控制信号串到所有数组数据选择路径，但前提是后续所有使用都检查 count/valid。

测试不要只看 count；应逐项对比 PC、机器码和错误位。可用一个软件数组作为参考模型，随机执行 pop/push/flush，并在每拍比较。第 16 章已经提供这样的简单队列测试。

## 20.8 两阶段重定向如何理解

本项目把 redirect 决策及其数据再寄存一次，用于缩短路径：

```systemverilog
fetch_redirect <= redirect;
fetch_redirect_pc <= redirect_pc;
if (fetch_redirect) f_pc <= fetch_redirect_pc;
```

小心 `redirect` 和 `fetch_redirect` 不是同一个沿前事件：前者是本拍 EX/trap 决策，后者是之前登记的前端重定向。`front_flush = redirect || fetch_redirect`，因此清理覆盖两个阶段。

当 redirect 决策本拍恰好接收了一个指令请求，项目 [535–539 行](../rtl/rv32_core.sv#L535-L539) 保存该请求但设置 `q_killed <= redirect`；已经被对端接收的请求不能撤销，必须把将来的响应接收并丢掉。随后 `fetch_redirect` 把正确目标装进 f_pc。

自己动手测试时，用一个可延迟指令响应的模型：

1. 让错误路径请求确实被接受。
2. 在其响应前触发分支重定向。
3. 使旧响应稍后到达。
4. 断言旧响应未产生退休，正确目标之后能继续。
5. 再构造响应与 redirect 同拍，确认 count 清空优先级。

不要拿纯组合的 `if (branch) PC=target` 代替此协议：那会丢掉对已接收事务的责任。

## 20.9 两路配对：先判断年龄，再判断通道

队列第 0 项较老，第 1 项较年轻。配对前先检查它们地址连续：

```systemverilog
id_second_valid = fetch_count >= 2 && fetch_pc[1] == fetch_pc[0] + 32'd4;
```

元数据中辅助 ALU 可处理的简单指令有明确条件：合法、非 serial、写寄存器、ALU 操作不超过基础 COPY，并排除 Load/Store/M/分支跳转。不要把它简化成“opcode 看起来像整数运算”；实际可配对集合以 [issue_metadata](../rtl/rv32_core.sv#L67-L77) 为准。

`pair_dependency` 比较年长指令的 rd 与年轻指令实际使用的 rs1/rs2，以及年轻的写回 rd，阻止组内 RAW/WAW。若不允许配对，仍可单独发射队首；第二项留在队列。

举三组：

```asm
addi x5,x0,1
addi x6,x0,2        # 独立，可能配对；仍要满足预测等条件

addi x5,x0,1
add  x6,x5,x5       # 组内 RAW，不配对

addi x5,x0,1
addi x5,x0,2        # 组内 WAW，不配对
```

请自己根据 `pair_normal` 与 `pair_swap_candidate` 为每组填写每一项布尔条件。你会发现“可以双发射”是多条件共同的结果，不是看到两条指令就必定发两条。

## 20.10 普通配对和交换配对

普通配对将年长指令放完整通道，年轻的简单指令放辅助通道。交换配对允许**年长简单指令**走辅助通道，而让年轻的 Load/Store/乘除/分支等有机会使用完整通道。

实际 `pair_swapped = pair_swap_candidate && !pair_normal`；如果普通配对已经可行，优先普通。对于交换，EX 捕获时互换载荷：

```text
物理主通道 x_*：队列第 1 条（年轻）。
物理辅助 x_second_*：队列第 0 条（年长）。
x_swapped：记录这次映射。
```

从 [579–598 行](../rtl/rv32_core.sv#L579-L598) 找出 PC、机器码、译码、操作数和预测各自怎样选择。你自己的 RTL 至少要保证这些字段被同一个 swap 条件一致选择，否则可能出现“用年轻译码执行年长指令”的隐蔽错配。

随后把交换标志带到 MEM：`m_swapped <= x_swapped`。WB 用它把 PC、insn、rd、result 恢复为程序顺序。对照 [633–645 行](../rtl/rv32_core.sv#L633-L645)；不要在 EX 交换之后忘记在退休处交换回来。

## 20.11 两路旁路的数据优先级

主通道操作数 `a/b` 从保存的 `x_a/x_b` 开始，依次可被下面的数据覆盖：

```text
较老 WB 第一口 → WB 第二口 → 较新 MEM 主通道 → MEM 辅助通道 → x0 强制 0
```

这段顺序就是 [245–275 行](../rtl/rv32_core.sv#L245-L275) 中的赋值顺序；并非所有来源都能同时构成合法同 rd 的生产者，要结合 valid、write、配对约束和交换关系理解。辅助执行通道的两个操作数也有类似选择，见 [357–379 行](../rtl/rv32_core.sv#L357-L379)。

索引相等比较提前一个阶段寄存，保存在 `forward_m0/m1/w0/w1`；EX 使用时再结合当前 valid、write、Load/MUL 等条件。这样做为了缩短比较到 ALU 的路径，但要求在 EX 或 MEM 暂停时比较的是正确的 held/next 编号。自己初次实现可以先写清晰的当拍比较，验证正确后再研究该优化。

## 20.12 Load 数据为什么可以先进入旁路选择器

项目代码注释指出：数据 mux 可能在 Load 尚未完成时选到暂时无效的 `mem_result`。这不等于允许消费者推进，因为 `hazard`、`m_ready` 和错误时的 `mem_trap` 共同控制执行/副作用。

简化地分析一条依赖 Load：

```asm
lw  x5,0(x1)
add x6,x5,x5
```

- Load 在 MEM 等待时，后面的 ADD 可位于 EX，但依赖值尚不可用，必须停住。
- 若 `LOAD_BYPASS=1` 且响应成功完成，可以从 MEM 的 Load 结果给 EX 使用。
- 若关闭旁路，消费者继续等结果进入 WB。
- 若响应错误，`mem_trap` 不能让依赖指令产生正常结果或副作用。

测试既要比退休结果，也要把响应延迟、响应错误和 `LOAD_BYPASS` 参数组合覆盖。不要仅观察组合线 `a` 某拍是什么值，就判断架构行为已经错误；关键是这个值在**什么时候被允许消费**。

## 20.13 旁路结果如何跨过长暂停

假设 EX 因 MEM 长等待而停住，WB 在某一拍有正确的寄存器结果，可临时旁路到 EX。但下一拍 WB 可能已变成无效，如果 EX 仍然停住，原先捕获的 `x_a` 还是旧值。

项目在 EX held 时把当前已选择的操作数写回 EX 寄存器：

```systemverilog
end else if (x_valid) begin
    x_a <= a; x_b <= b;
    x_second_a <= a_second; x_second_b <= b_second;
end
```

这样即使产生旁路的 WB 已离开，等待中的指令还保留观察过的值。定向测试应让指令真正停过 WB 退出的那一拍；只有“某拍发生暂停”的覆盖并不足以证明这个问题。

## 20.14 EX 到 MEM 的握手和副作用

项目 `x_go` 不只是 `m_ready`：它还检查 hazard、early LSU 的请求接收，以及除法完成/保存。`EARLY_LSU=1` 时，数据请求从 EX 发出；同时受指令有效、无本地异常、对齐、无更老 trap、中断、hazard 和 MEM 可接收等条件限制。准确公式见 [402–443 行](../rtl/rv32_core.sv#L402-L443)。

当 `EARLY_LSU=0`，请求由 MEM 发，`m_sent` 防止重复。提前发射能够缩短某些 Load 延迟，但更老异常出现的同一周期若仍让年轻 Store 握手，就会产生不可撤销副作用；因此不能只为了跑快删除门控。

动手时先把一条 Store 可能握手的所有条件写在白板上，再做两类测试：

1. ready 连续为 0 多拍，确认地址/数据/strobe 与上下文不丢。
2. 更老 Load 错误与年轻 Store 同时接近可推进，确认 Store 没有被设备接受。

第 19 章的简化流水版已经提供第二类思路，但真实的 early LSU 需要自己的定向用例。

## 20.15 MEM 完成与 trap 的区分

```systemverilog
m_finish = m_valid && (m_exception || !(m_load || m_store_en) ||
                      (d_rsp_ready && d_rsp_valid)) &&
                      (!m_mul || m_funct3 == 0 || mul_high_ready);
mem_trap = m_finish && (m_exception || ((m_load || m_store_en) && d_rsp_error));
```

正常 ALU 指令可完成；访存等待响应；已经记录的异常不必再发正常访存；高位乘法可能等待结果就绪。完成只是“这组从 MEM 离开”，不总是“主通道正常退休”：若 `mem_trap=1`，需要按年龄规则抑制正常副作用或保留交换组中较老的辅助指令。

`trap_pc/cause/value` 由同步异常和中断路径产生，详细编码在第 11 章。尤其是数据总线报错：cause 取 Load access fault 或 Store access fault，`trap_value` 是原始有效地址而不是 word 对齐后的总线地址。

## 20.16 交换组里年轻指令出错

设程序顺序为 A、B：

```asm
addi x5,x0,1       # A 年长，简单，走辅助通道
lw   x6,2(x0)      # B 年轻，走主通道；不对齐
```

如果满足交换配对条件，A 是辅助通道，B 是主通道。B 发生异常不能取消 A 已应有的架构结果。项目使用：

```systemverilog
m_second_valid <= x_go && x_second_valid &&
                  (!x_exception || x_swapped) && !mem_trap && !irq_take;
...
w_valid <= m_finish && (!mem_trap || (m_swapped && m_second_valid));
w_second_valid <= m_finish && !mem_trap && m_second_valid;
```

这里 `x_swapped/m_swapped` 让年长 A 得以保留，年轻 B 不作为正常第二条退休。准确结果还取决于该实际程序是否在某次运行中被配对；构造回归时应检查交换配对确实发生，否则测试可能只覆盖单发射。

反过来，若普通配对中的年长主通道出错，年轻辅助不能退休。把两种测试的 A/B 年龄写清楚，比单纯按 lane 0/lane 1 写期望可靠。

## 20.17 输出退休流并检查

项目对外输出：

```systemverilog
assign retire_valid = w_valid;
assign retire_pc = w_pc;
assign retire_rd = w_write_rd ? w_rd : 5'b0;
assign retire_data = (w_write_rd && w_rd != 0) ? w_result : 32'b0;
assign retire_second_valid = w_second_valid;
assign retire_second_pc = w_pc + 32'd4;
```

第二口有效时，测试模型先处理第一口，再处理第二口。无写回的分支/Store 仍可正常退休，`rd=0` 不能等同于 `valid=0`。trap 走独立观测信号，参考模型必须知道异常何时发生以及架构状态如何更新。

自己调试时推荐记录：

```text
cycle | first valid,pc,insn,rd,data | second valid,pc,insn,rd,data | trap
```

发现差分第一处不一致，先从该条的 PC/机器码查队列、EX 载荷、旁路、MEM 和 WB，而不是先看最终寄存器。最终值可能被后续指令覆盖，掩盖更早多退休或错路径 Store。

## 20.18 收尾：按最小差异方式做实验

选一个修改目标，例如“给自己的第 19 章核心加 WB→读口旁路”：

1. 先保存当前版本，并用原测试记录结果。
2. 加一条同拍读写的定向程序，确认未优化时能通过、但存在等待。
3. 在读口选择写回值，修改对应 hazard 条件；不要同时加 MEM 旁路。
4. 观察退休序列与值不变，统计等待是否减少。
5. 再加冲刷、错误、x0、两次写同一 rd 的测试。
6. 通过后才进入下一项优化，最后与项目完整条件比较。

反复做这种小步验证，比一次性抄入整份真实核心更容易定位 bug。实现全部扩展、两路、CSR 和板级系统仍是一个工程，不是完成这一章就自动结束；项目回归和赛题证据按第 14、15、18 章分别闭合。
