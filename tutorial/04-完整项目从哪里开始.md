# 4. 完整项目从哪里开始

前面三个实验故意绕开了 CPU 最难的部分：同一时间只有一条指令在工作，取指和数据读取看起来也没有排队。现在我们的目标变了：**解释并重建本仓库的青龙 CPU 与最小 SoC**，而不是继续往 `small_cpu.sv` 的 case 中堆功能。

先不要新建一个 600 行的 `core.sv` 然后尝试一次写完。项目的 [rv32_core.sv](../rtl/rv32_core.sv) 同时处理了取指、队列、两路发射、旁路、访存、异常和预测，直接照着从第一行抄到最后一行很难知道每个条件为何存在。我们要先确定外部可观察的行为，再一点点把并行性加进去。如果想马上动手体验这个接口，先运行 [第 17 章的多周期核心](17-多周期核心实战.md)，再回来沿主线阅读。

这章会给出具体的目标接口、模块顺序和每一阶段的检查点。后续章节逐段实现各部分，并在需要与当前 RTL 严格一致时给出对应源码位置。

## 4.1 先看一条真实程序如何经过整个系统

假设 CPU 执行：

```asm
addi x1, x0, 64
lw   x5, 0(x1)
add  x6, x5, x5
sw   x6, 4(x1)
```

我们想看到的是：内存地址 64 的数被读出、乘 2、写到地址 68。实际上有很多问题必须得到答案：

- 第一条指令尚未写回时，Load 怎么读到新的 x1？
- Load 还没等到 RAM 响应，ADD 会不会用到旧的 x5？
- 若 Load 的地址无效，后面的 Store 能不能已经写出去了？
- 若下一条指令先被取到，但后来发现分支预测错了，怎么丢掉它？
- 如果一个时钟发射或退休两条指令，哪个才是程序中的较老者？

**这些问题构成了项目的主体。**译码告诉我们指令意图；流水线和总线必须保证这些意图在正确的时间、以正确的程序顺序生效。

## 4.2 目标功能要说清楚

根据项目 [README](../README.md) 和现有 RTL，目标系统包括：

- 32 位 RISC-V 核心，支持 RV32IM、Zicsr、Zifencei、Zba 和 Zbb；具体合法编码要以实现和规范共同核对。
- 逻辑上的 IF1、IF2、ID、EX、MEM、WB 六级，顺序发射、顺序退休，最多两条同周期发射和退休。
- 寄存器旁路、Load 等待、分支预测、精确异常和 M-mode 中断。
- 最小 SoC：64 KiB 统一 TCM、UART TX、GPIO、计时器和软件中断。
- 可选 DDR 系统是独立配置，包含额外桥、时钟和 IP；不能由默认 TCM 仿真推断板级成功。

它没有因具备 DDR 就自动具备 Cache，也没有完成端到端 AI 应用。赛题高阶提出的 Cache 和 AI 是额外工作，第 15 章单独讨论。

本教程会带你重建同等功能的阶段式实现并逐段对照实际 RTL。**功能等价**不代表每个周期的取指决策都相同，更不代表资源和频率自动一致：要与仓库完全同周期同结果，必须采用相同参数、接口、控制优先级、RTL 与工具配置，并分别验证。

## 4.3 先画出模块，而不是先画所有寄存器

```text
                  ┌────────── rv32_core ────────────┐
                  │                                 │
 instruction bus ─┤ 取指/队列 → 译码 → EX → MEM → WB ├─ retirement
                  │     ↑          │          │      │
                  │ predictor   ALU/divider   CSR     │
                  └────────────────┼─────────────────┘
                                   │ data bus
                                   ▼
                        qinglong_soc: TCM / UART / GPIO / timer
```

这里先把验证接口 `retirement` 画在外面，是因为它是我们检查结果的稳定观察点：一条指令在 EX 算出结果，不代表它最终一定生效；在 WB 按架构顺序退休时，才可以与顺序参考模型比较。

本仓库文件的依赖次序见 [rtl/files.f](../rtl/files.f)。顺着这个次序，我们要分别实现：

1. `rv32_pkg.sv`：ALU 操作常量与译码结果结构。
2. `rv32_decode.sv`：把 32 位机器码变成控制字段。
3. `rv32_alu.sv`：整数运算；单独测试而不依赖整个核心。
4. `rv32_predictor.sv`、`rv32_divider.sv`、`rv32_csr.sv`：预测、多周期除法与架构控制状态。
5. `rv32_core.sv`：把上述模块和前端、执行、访存、提交控制串起来。
6. `uart_tx.sv`、`qinglong_soc.sv`：让 CPU 真正连到内存和设备；可选外部存储使用额外模块。

第一次做自己的实验时可以按这个划分新建 `my-rv32/rtl` 和 `my-rv32/tb`，不要覆盖仓库的现成 RTL；也不要把旧的综合生成文件和手写源同时加入同一工程。

## 4.4 关键边界一：指令接口

先看核心 [端口声明](../rtl/rv32_core.sv#L1-L43)：

```systemverilog
output logic        i_req_valid;
input  logic        i_req_ready;
output logic [31:0] i_req_addr;
input  logic        i_rsp_valid;
output logic        i_rsp_ready;
input  logic [63:0] i_rsp_data;
input  logic [1:0]  i_rsp_error;
```

请求给出一个字节地址。响应包含两个 32 位指令字及两个分别的错误位：低半对应请求 PC，高半对应 PC+4。前端根据预测结果决定是否需要第二条；即便一起返回，也不意味着必定一起发射。

本项目每个端口最多一笔未完成事务；响应在请求接收后最早下一周期出现，并保持到对方接收。指令请求**接受前可以取消**，例如发生重定向时；接受后的响应则仍须处理，必要时标记 killed 并丢弃。这个接口是项目自定义契约，不能随手接到要求 valid 必须一直保持的 AXI master 端口。

第 7 章会逐周期画出：保存 `q_pc`、请求接受、前端预测继续变化、旧响应晚到时如何仍然知道它属于哪个 PC。

## 4.5 关键边界二：数据接口

```systemverilog
output logic        d_req_valid;
input  logic        d_req_ready;
output logic [31:0] d_req_addr, d_req_wdata;
output logic [3:0]  d_req_wstrb;
output logic        d_req_write;
input  logic        d_rsp_valid;
output logic        d_rsp_ready;
input  logic [31:0] d_rsp_data;
input  logic        d_rsp_error;
```

数据端同样先请求、后响应，每端口最多一笔在途。请求包含对齐字地址、写数据和每字节使能。CPU 要保存原始有效地址低位，Load 返回后才能选择正确字节并符号扩展。数据请求在等待接收期间需要保持必要载荷；项目的非对齐访问形成异常而不拆分。

第 9 章会说明为何 `d_req_valid` 同时受 `x_valid`、对齐、hazard、较老异常和中断等条件约束。仅靠给 `mem_we` 加一个 valid 并不足够。

## 4.6 关键边界三：退休与陷阱

项目给出两个按程序顺序排列的退休口：

```text
retire_valid / retire_pc / retire_insn / retire_rd / retire_data
retire_second_valid / retire_second_pc / retire_second_insn /
retire_second_rd / retire_second_data
```

不写寄存器的正常退休指令也必须能被观察；`rd=0` 不应被理解为“没有退休”。若一拍两条，参考模型先处理较老的第一条，再处理较年轻的第二条。

异常另有 `trap_valid / trap_pc / trap_cause / trap_value`。例如 Load 不对齐时不能把正常 Load 的退休结果和错误陷阱同时当成成功结果。遇到较老故障，较年轻指令不能产生架构副作用；但交换发射通道后年轻的 Load 故障时，较老的简单 ALU 仍可能需要正确退休。第 10、11 章将分开处理这两种年龄关系。

## 4.7 从哪一个可验证版本开始

建议把目标拆成以下**能运行并检查的版本**，每完成一个版本保留源码和日志；不要为了赶进度跳过回归：

### 版本 A：译码器与单元

写 `rv32_pkg`、`rv32_decode` 和基础 ALU；输入 32 位指令，检查控制、立即数、合法性以及 signed/unsigned 结果。程序不能从中直接运行，但错误可定位在单一模块。

### 版本 B：保守的单发射核心

保持最多一条指令在关键路径中，指令和数据总线按上面的握手工作。先不预测、不双发射，加载短汇编程序，逐条核对退休 PC、rd 和数据。把错误响应和对齐情况单独测试。

### 版本 C：单发射六级流水线

加入每级 valid 和 hold/flush，先用保守暂停保证正确，再按 WB、MEM、Load 响应顺序增加旁路。让总线随机等待；同一程序与版本 B 的退休流一致。不能只比较最终寄存器，因为多退休一条错误路径指令可能被后来覆盖。

### 版本 D：队列与双发射

先让四项队列仍单发射，验证接收响应、同周期出入和清空；随后引入正常配对和物理交换。看退休口顺序和异常年龄，检查必须分组的 RAW/WAW。预测继续保持关闭，减少同时变化的变量。

### 版本 E：系统功能与优化

补上 CSR、异常、中断、M 扩展、Zba/Zbb、动态预测、`FENCE.I`，并验证它们与暂停、双发射交互。然后连接 TCM、UART、GPIO、启动固件，最后运行项目回归、综合和板测。

版本 D/E 的先后可以调整：例如先在单发射加入异常更容易观察。关键是不漏掉最终的组合测试，也不把某一中间版本当作已完成赛题。

## 4.8 看源码时如何不迷路

项目核心的命名可以帮助我们把指令放回正确位置：

```text
f_          前端准备发出的取指 PC
q_          已接受、仍在等待响应的取指请求上下文
fetch_      最多四项的取指队列
id_         队首正在译码/考虑发射的指令
x_          EX 指令及操作数
m_          MEM 指令、地址、异常和等待状态
w_          WB 即退休阶段
*_second    通常表示辅助物理通道；退休 second 则表示程序中第二条
```

特别注意：`q_valid` 是**取指请求上下文有效**，不是队列非空；队列是否有指令由 `fetch_count` 表示。不要把 `x_second` 的物理通道编号等同于指令年龄，物理通道可以交换。

后面章节会反复以“本字段属于哪条指令、何时更新、valid 为多少、什么事件清除它”四个问题阅读每一段代码。这比记住名字更重要。
