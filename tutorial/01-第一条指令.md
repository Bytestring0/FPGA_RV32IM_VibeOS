# 1. 第一条指令：做一个只会加法的 CPU

这一章结束时，你会看到终端输出：

```text
pc=0 instruction=00700293
pc=4 instruction=ffd28313
...
PASS addi_cpu: x5=7 x6=4 x7=1 pc=16
```

这里不是在运行 Python 程序。我们写的是一个电路模型：每个时钟上升沿，它从当前 PC 所指的位置读一条机器指令，计算并保存结果，再把 PC 加 4。先做到这一件小事，后面再把它改成真正能等待内存、能处理多条在途指令的 CPU。

## 1.1 你要先装什么

需要一个支持 SystemVerilog 的仿真器。示例使用 Icarus Verilog 的 `iverilog` 和 `vvp`；可以在 Windows PowerShell 中运行，也可以在 Linux/WSL 中运行。先检查：

```powershell
iverilog -V
vvp -V
```

如果系统说找不到命令，先安装 Icarus 并把其 `bin` 目录加入 PATH，再重新打开终端。不要继续复制后面的命令期待它自动安装工具。以下命令从**本教程目录**执行；如果你在工作区根目录，先运行：

```powershell
Set-Location D:\FPGA\RiscV\tutorial
```

`D:\FPGA\RiscV` 是本机项目路径；在其他机器上换成你的实际路径。编译输出放到当前用户临时目录，而不是覆盖项目文件：

```powershell
iverilog -g2012 -s addi_tb -o "$env:TEMP\addi_cpu.vvp" `
  examples/01-addi/addi_cpu.sv examples/01-addi/addi_tb.sv
if ($LASTEXITCODE -ne 0) { throw '编译失败' }
vvp "$env:TEMP\addi_cpu.vvp"
if ($LASTEXITCODE -ne 0) { throw '仿真失败' }
```

Icarus 可能打印 `sorry: constant selects in always_* ...`。本例中它说明仿真器扩大了组合块的敏感信号范围；不能把所有 `sorry` 都忽略，应结合完整消息和退出码判断。看到了 `PASS` 且进程成功退出，才代表这个 testbench 的检查通过。

如果你更熟悉 WSL，把续行符反引号换成反斜杠，输出路径例如 `/tmp/addi_cpu.vvp`；不要把 PowerShell 的 `$env:TEMP` 直接复制进 Bash。

## 1.2 一条指令到底在要求电路做什么

先看第一条：

```asm
addi x5, x0, 7
```

它的意思是“读取 x0，加上立即数 7，将结果写到 x5”。这里 `x0` 到 `x31` 是架构定义的 32 个寄存器名，可以把每个寄存器想成能保存 32 个 0/1 的小盒子。`x0` 特殊：无论写入什么，读它永远得到 0。

因此执行前如果 PC 为 0，执行后：

```text
x5 = 0 + 7 = 7
PC = 4
```

为什么 PC 加 4？本实验只用 32 位、也就是 4 字节长的指令，PC 是**字节地址**。如果支持 16 位压缩指令，顺序增量就不总是 4；本项目没有实现 C 扩展，所以这里按 4 字节对齐。

下一条是 `addi x6,x5,-3`。它必须读取刚才写入的 x5，得到 `7 + (-3) = 4`。第三条向 x0 写入的结果要被丢弃；第四条再读取 x0 来证明确实仍为零。

## 1.3 汇编文字怎么变成 32 位

电路收到的不是字符串 `addi x5,x0,7`，而是 `0x00700293`。ADDI 属于 I 型：

```text
31              20 19      15 14  12 11       7 6        0
+------------------+----------+------+----------+----------+
|   imm[11:0]      |   rs1    |  000 |    rd    | 0010011  |
+------------------+----------+------+----------+----------+
```

对 `addi x5,x0,7` 逐个填入：

```text
imm = 7   → 0x007 << 20 = 0x00700000
rs1 = 0   → 0     << 15 = 0x00000000
funct3=0  → 0     << 12 = 0x00000000
rd  = 5   → 5     <<  7 = 0x00000280
opcode    →                 0x00000013
按位组合后                 0x00700293
```

立即数只有 12 位。负数使用补码，例如 `-3` 的 12 位形式是 `0xffd`；放进 32 位时，要复制符号位 20 次：

```systemverilog
wire [31:0] imm = {{20{insn[31]}}, insn[31:20]};
```

如果最高位是 1，扩展为 `0xfffffffd`；32 位加法自然得到模 2³² 的结果。写成 `{20'b0, insn[31:20]}` 会把 -3 错误地当成 4093。后面译码器要做更多格式的重排，这一条先理解清楚。

## 1.4 看核心：每个信号是什么

打开 [addi_cpu.sv](examples/01-addi/addi_cpu.sv)。先看接口：

```systemverilog
input  logic        clk, rst;
input  logic [31:0] insn;
output logic [31:0] pc;
output logic        halted;
```

`clk` 是时钟；`rst=1` 表示同步复位；`pc` 告诉外部要取哪条指令；`insn` 是外部根据 PC 返回的指令。`halted` 只是教学程序遇到不认识的指令时停下来的标记，不是 RISC-V 异常接口。

试着顺着代码读：

```systemverilog
wire [4:0] rd  = insn[11:7];
wire [4:0] rs1 = insn[19:15];
wire [31:0] a = (rs1 == 0) ? 32'b0 : regs[rs1];
```

这里并没有“执行”指令。它只是从指令位中接线拿到寄存器编号，再决定第一个操作数。`regs[rs1]` 的索引是 0～31；当 `rs1=0` 时直接返回 0，不依赖数组中 x0 的实际内容。

判断是否是本实验支持的 ADDI：

```systemverilog
wire is_addi = (insn[6:0] == 7'h13) && (insn[14:12] == 3'b000);
```

光检查 opcode 不够：同一 opcode 下 `funct3` 还区分其他立即数运算。当前版本只认识 funct3 为 0 的 ADDI，其他编码停机。

## 1.5 时钟沿上发生的事

核心状态在这个块中更新：

```systemverilog
always_ff @(posedge clk) begin
    if (rst) begin
        pc <= 0;
        halted <= 0;
        for (i = 0; i < 32; i = i + 1) regs[i] <= 0;
    end else if (!halted) begin
        if (is_addi) begin
            if (rd != 0) regs[rd] <= a + imm;
            pc <= pc + 32'd4;
        end else begin
            halted <= 1;
        end
    end
end
```

`<=` 是非阻塞赋值。可以先把它理解为“在这次时钟沿，根据旧状态计算所有右侧值，然后一起更新左侧寄存器”。不是先把 PC 改成 4，然后用地址 4 的指令完成同一拍的加法。

复位时这个教学核心把所有寄存器清零，只是为了让最初实验更直观；RISC-V 不要求 x1～x31 在复位后为零，青龙项目也不保证它们复位为零。正式软件要自己初始化需要的寄存器。

注意本模型把指令读取写成组合逻辑：PC 一变，testbench 立即给出 ROM 内容。这简化了第一课，却不等价于 FPGA 同步 RAM。后面会让请求和响应分开。

## 1.6 Testbench 如何判断不是“看起来运行了”

打开 [addi_tb.sv](examples/01-addi/addi_tb.sv)。它做四件事：

1. 每 5 ns 翻转一次 `clk`，构成 10 ns 周期。
2. 开始时保持复位，并在下降沿释放，避免与 DUT 采样上升沿竞争。
3. 把 PC 当成字节地址，使用 `pc[31:2]` 查 ROM。
4. 当 DUT 停机后检查 PC 和各寄存器；任何不符都 `$fatal(1, ...)`，超时也会失败。

使用 `$display("PASS ...")` 并不自动证明正确：关键是前面那些 `!==` 检查真的检查了期望状态。这里的期望来自我们独立手算的四条指令，而不是从 DUT 的计算结果复制过来。

`!==` 与 `!=` 不同：如果信号含 X 或 Z，前者能把它当成不匹配。硬件仿真中未知值很重要，不要让它悄悄通过检查。

## 1.7 自己改一次，再解释结果

先把 `rom[1]` 改成 `32'hffe28313`。它的立即数是 `0xffe`，也就是 -2。如果其余不变，x6 应变成 5，原 testbench 会故意报错。然后修改期望值，重新运行，确认 PASS；最后恢复原文件。

再把核心里 `if (rd != 0)` 暂时去掉。只看 x0 的读口可能仍然是零，因为读 x0 时被强制返回了 0；但数组 `regs[0]` 已被意外修改，本 testbench 会发现。这个实验说明：一个性质可能由两处机制保护，测试时应知道自己观察的是哪一层。
