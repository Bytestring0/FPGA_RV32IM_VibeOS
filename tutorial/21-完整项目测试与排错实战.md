# 21. 完整项目测试与排错实战：从第一条错误退休开始

前面已经从指令、单元、流水线、SoC 讲到 FPGA。真正自己动手重建时，最费时间的往往不是写出一条 `assign`，而是出现错误后不知道它属于哪一层。这章用仓库实际测试入口和参考模型，示范如何让一个失败可复现、定位到最早出错的指令，再缩小到具体模块。

前提：在独立工作副本中运行，不要并行改写同一个 `build/firmware.hex`。本章示例的日志名称取自项目脚本，路径请按实际复制位置调整。记录每次测试的源码版本、参数、工具版本、固件和随机种子；没有这些信息，几天后很难确定“同一个错误”是否真的相同。

## 21.1 用分层测试代替一次跑所有东西

```text
第 1 层：译码、ALU、除法、CSR 等单元定向输入输出。
第 2 层：指令小程序，逐条检查退休结果和分支路径。
第 3 层：随机总线等待、两口退休、独立架构参考模型。
第 4 层：异常/中断、串行、双发射/旁路边界专项。
第 5 层：SoC 的 RAM、UART、设备寄存器和固件启动。
第 6 层：综合、布局、时序、上板与外设实际行为。
```

低层通过不保证高层通过；高层失败也不应立即改低层代码。比如串口没有字符，可能是固件没有开始、UART 波特率错、针脚错，甚至下载的是旧位流；先找到第一处失去可观察行为的位置。

第 5、6、11、12 章给了单元实验，第 14 章列了项目回归。第 17、19 章两个小核心的测试可以作为练习，但它们不是完整项目的参考实现。

## 21.2 跑项目回归之前检查环境

在隔离副本的 WSL 终端：

```bash
command -v make
command -v verilator
command -v riscv64-unknown-elf-gcc
command -v riscv64-unknown-elf-objcopy
python3 --version
verilator --version
riscv64-unknown-elf-gcc --version
```

工具命令存在只证明可执行文件可找到，还需确认使用了正确版本/目标参数。项目工具前缀虽然叫 `riscv64-unknown-elf-`，实际固件编译指定 RV32 与 ILP32；如果赛方明确要求另一名称的工具链，必须向组织方确认，不可自行认定完全等价。

按第 14 章准备依赖后顺序执行：

```bash
make lint
make check
```

`make lint` 的 `-Wno-fatal` 使某些告警不导致非零退出，因此 `exit 0` 不是“零警告”。记录和分析告警，特别是宽度、截断、未驱动和 latch；本次运行已有宽度类提示。

`make check` 会运行 smoke、ISA、trap、interrupt、dual-stress、differential、UART 等目标。一个目标通过并不能证明其他目标执行了。测试脚本会跳过不适用的 `ma_data`；这是精确非对齐异常与该上游用例的预期不同，不能把它计作通过。

## 21.3 从一条独立汇编用例开始

当一个大程序报错，先写只包含故障所需指令的汇编，例如验证最近写者：

```asm
addi x5, x0, 11
addi x5, x0, 22
add  x6, x5, x5
```

期望 x6 是 44，不是 22。仅有三条指令还不一定能自动结束：完整测试需包含合适的初始化和项目使用的退出机制。参考 [启动代码](../sw/start.S)、[链接脚本](../sw/link.ld) 和 [现有压力测试](../tests/dual_issue_stress.S)，不要凭空假设仿真器会在 ELF 尾部停止。

用 `objdump -d` 检查生成的实际机器码。你写的伪指令可能展开为多条指令，压缩指令或链接重排也可能使你以为的 PC 不对应；目标选项需与核心支持的 ISA 一致。

针对一次 bug 只保留必要的指令和延迟环境，再加入一条会触发错误的因素，例如同 rd 的两个不同写者、Load 返回延迟或交换配对。缩小用例必须保留失败；删到不再失败时，刚删掉的因素可能正是必要条件。

## 21.4 差分模型实际检查了什么

项目 [sim/core_main.cpp](../sim/core_main.cpp) 有一个 `Oracle`：维护独立的寄存器、字节内存和 PC。在每条退休时：

1. 从参考内存按参考 PC 取指。
2. 比较 DUT 的退休 PC 和机器码。
3. 自己解释算术、分支、访存和支持的扩展。
4. 比较目的寄存器编号和结果。
5. 更新参考寄存器、PC 和退休数。

同拍两条退休时先调用第一口，再调用第二口，因此第二条看到第一条的架构效果。脚本还检查不能只出现第二口而没有第一口。

这是重要验证，但不是万能证明：CSR 结果在该模型中没有独立全面计算，异常另由 trap 用例覆盖；模型对部分 MMIO 数据也采用特殊处理。随机程序和上游测试只能覆盖实际运行到的指令及交互，不能据此宣称所有时序或外设行为已证明正确。

## 21.5 为什么必须独立建参考模型

如果参考模型直接调用 DUT 的 ALU 或复用完全相同的立即数拼接函数，同一个错误可能同时出现在 DUT 和参考侧，比较仍通过。项目用 C++ 独立解释指令，而不是调用 SystemVerilog 译码器，正是为了降低共同错误风险。

参考模型自身也可能出错：对发生差异的一条指令，应手算一次、对照 ISA 规范和工具反汇编，不要默认 DUT 或模型必有一方正确。尤其检查有符号比较、32 位溢出、除零、负数余数与不对齐异常。

## 21.6 随机等待如何揭示握手 bug

仿真循环在低电平准备响应与 ready，调用 `eval()` 计算组合结果，检查退休和握手，然后在高电平触发时序更新。指令和数据 ready 会随机延迟，响应也保存一个延迟计数；详见 [168–228 行](../sim/core_main.cpp#L168-L228)。

具体帮助发现：

```text
请求等待时地址改变：接收方可能看到错误事务。
Store valid 保持太久：同一写入被接收两次。
响应回来时上下文已被覆盖：Load 写错 rd。
旧响应与新请求同拍：请求记录被误清空。
分支改变路径后旧响应晚到：错误路径退休。
```

数据请求的背压稳定由测试显式检查；指令请求在本项目契约下接受前允许取消，不能直接套用要求 valid 永远保持到 ready 的总线断言。换成其他总线时，断言也要跟着接口契约改变。

## 21.7 复现随机差分失败

[scripts/run_differential.py](../scripts/run_differential.py) 对 ISA 程序和三个生成程序分别使用多个总线随机种子，失败会保存已收集的日志。先记录：

```text
输入二进制路径：
程序生成种子：
总线随机种子：
CPU 参数：DUAL_ISSUE / LOAD_BYPASS / EARLY_LSU / PREDICT / BTB_BITS：
第一次不一致的退休序号、PC、指令、rd、data：
```

如果已构建 `build/core/Vrv32_core`，可以在**同一独立副本**按脚本实际接口重跑指定二进制和种子：

```bash
build/core/Vrv32_core build/isa/你的测试.bin 42
```

将路径替换为失败日志里的真实文件。该程序可选的第三个参数是最大周期数；第四个附加参数会关闭退休 oracle，只有明确在做非差分专项时才用，不能把关闭检查后的退出 0 当成差分通过。

这条命令不会重新生成二进制或重建核心；修改源码/参数后必须执行正确的构建目标并核对构建日志，否则可能运行旧模型。

## 21.8 第一次不同：先判断是哪一类

差分日志通常包含 `refpc`、`dutpc`、参考/实际指令、rd、data 和退休口。分类如下：

### PC 和机器码先不一致

优先检查：

- 分支比较是有符号还是无符号；立即数是否正确拼接。
- EX 真实 next PC 与保存的 predicted next 是否一致。
- redirect 时队列清空，旧请求和旧响应是否被 kill。
- 指令响应的低/高字是否与 PC、预测和错误位一一对应。
- 同拍 pop/push 与 flush 的 count 更新优先级。

先找到参考流与 DUT 流**第一次**分叉的位置；之后连续几十条 PC 都不同通常只是同一个分支错误的后果。

### PC/指令相同，rd 不同

优先检查译码 `rd/reg_write`、写 x0 的处理、普通/交换通道的 WB 选择、双退休顺序。若 Store 的立即数低位被当成 rd，往往是忘了用 `reg_write` 限定。

### PC/指令/rd 相同，data 不同

按指令类别检查：

- ADD/SUB：输入 rs1/rs2、立即数、最近写者旁路和 ALU 操作。
- Load：有效地址、字节 lane、符号扩展、响应与原 rd 的绑定。
- JAL/JALR：写回是本条 PC+4，不是目标 PC。
- 乘除：有符号选择、边界情况、完成前是否推进、保存的除法结果。
- CSR：确认该用例使用哪个专门测试和预期，不依赖差分模型全面证明 CSR。

## 21.9 用一张表定位旁路错误

以 `x5` 的连续写入为例，给每拍记录：

```text
cycle  ID.pc  EX.pc/rs1  MEM.pc/rd/result  WB.pc/rd/result
       hazard  x_go  forward_m0/m1  forward_w0/w1  a/b
```

先检查执行指令看到的最近写者是哪条，再看实际选择的是哪条。若索引比较是前一拍寄存的，还要记录比较输入对应的是 held EX 还是新发射指令；一味只看结果 mux 会漏掉“比较位属于上一条”的问题。

若 bug 只在延迟很长时出现，观察 EX 停住期间 WB 何时消失，以及 `x_a/x_b` 是否保存过旁路值。若只在交换配对时出现，增加 `x_swapped/m_swapped` 和两物理通道的 PC/rd，先把年龄关系标出来。

## 21.10 用一张表定位访存错误

```text
cycle  EX.pc  MEM.pc  m_sent  m_load/store  m_addr/funct3
       d_req_valid/ready/addr/write/wdata/wstrb
       d_rsp_valid/ready/data/error  m_finish  mem_trap  x_go
```

对 Store，设备侧以请求握手数统计是否重复；对 Load，记录响应对应的地址、目的 rd 和转换后的数据。注意外部 `d_req_addr` 是对齐地址，而异常 `mtval` 使用原始地址；二者不是同一个信号。

对非对齐情况，先检查请求是否被抑制，再检查 trap cause/value；即使最终 trap 正确，如果错误 Store 已握手，仍是副作用错误。

## 21.11 用一张表定位错误路径退休

```text
cycle  f_pc  q_valid/q_pc/q_killed  i_accept/i_consume
       fetch_count  fetch_pc[0..3]  fetch_pop
       x_pc/x_pred/actual_next  redirect/fetch_redirect/front_flush
       retire_pc  trap_pc
```

把错误路径上第一条被接受取指的 PC 标出来，再标记它是被放进队列、被清掉，还是晚到后因 killed 丢弃。核对控制决策周期与登记的 `fetch_redirect` 周期，不要把两者视为同一寄存值。

如果测试从未实际接受错误路径请求，即使没有错误退休也不能证明 late-response 处理正确；专项测试需要覆盖计数或断言。

## 21.12 SoC 没有 UART 输出时

按最便宜的观察点向外检查：

1. 固件 ELF 的入口和链接地址是否与复位 PC 对应？`firmware.hex` 是否来自本次 ELF？
2. 复位是否释放，CPU 是否开始取指、退休？
3. 固件是否进入输出例程，MMIO 写请求是否成功握手？
4. UART 发送器是否接到正确时钟与配置，TX 波形是否有起始位？
5. 软件配置的时钟频率是否等于真实 CPU 时钟，波特率分频是否匹配？
6. 板级约束、管脚、电平与 USB 串口设备是否对应，终端是否在复位前打开？
7. 下载的位流、固件初始化文件和报告是否来自同一构建？

仿真通过但板上失败时，先核对时钟、约束、复位、资源初始化、物理布线及下载来源；不要只盯着 ISA 译码。DDR 模型成功也不能证明加密 PHY 校准，见第 18 章。

## 21.13 最终留档

一次可信的完成记录至少写明：

```text
源码版本与未提交修改：
CPU/SoC 配置及工具版本：
固件源、编译参数、镜像哈希：
单元 / ISA / 差分 / trap / 中断 / UART 的结果与跳过项：
随机种子、覆盖统计、未解决警告：
PDS 工程、目标器件、时钟与约束：
综合资源、setup/hold 时序和报告路径：
位流哈希、下载方式、板型、串口原始日志：
基准版本、迭代数、周期、实际频率、耗时和成绩计算：
已知缺项（如 Cache、AI 应用、长期稳定性）：
```

任何历史记录只能证明**对应的源码/参数/位流和测试条件**。改了 RTL 或固件后，要重跑与改动有关的功能回归，并重新生成需要的时序和板测证据；不要把旧 102 MHz TCM 数据自动贴到新 DDR 系统上。
