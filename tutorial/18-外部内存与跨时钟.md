# 18. 可选 DDR 路径：从 CPU 的一字请求走到 256 位接口

默认 SoC 用 64 KiB TCM，已经能跑前面的固件。项目还有可选 DDR 接入：代码不只包括一个宽存储器端口，还要解决指令/数据仲裁、32 字节边界、两个时钟域和厂商控制器的特殊握手。

先强调现状：这是**无缓存** DDR 窗口，一次只有一笔外部事务，不是赛题要求的两路组相联 I/D Cache。仓库文档记载独立 IP 示例布局通过，但 CPU+DDR 整体时序和实板状态需以最新报告为准，不能从协议仿真推断 PHY 已校准或板测通过。

完整路径：

```text
CPU 指令/数据请求
    ↓
qinglong_soc 的地址选择：0x80000000–0xbfffffff 且 DDR_ENABLE
    ↓
qinglong_extmem：双端口仲裁，32 位 ↔ 256 位，跨行取指
    ↓ CPU 时钟域
qinglong_hmic_bridge：握手邮箱 + 超时/故障处理
    ↓ UI 时钟域
厂商 HMIC_S 控制器 + PHY → DDR3 颗粒
```

请依次阅读 [qinglong_extmem.sv](../rtl/qinglong_extmem.sv)、[qinglong_hmic_bridge.sv](../rtl/qinglong_hmic_bridge.sv) 和 [DDR 接入报告](../docs/板载DDR3接入与验证.md)。这章解释怎样实现仓库已有适配路径，不教你凭空自制 DDR3 PHY；控制器/PHY 属于厂商 IP。

## 18.1 先冻结地址和粒度

启用 DDR 后，`0x80000000`–`0xbfffffff` 是 1 GiB 地址窗口。适配器将 CPU 的字节地址去掉窗口前缀，形成低 30 位的窗口偏移。下级一次事务覆盖 32 字节：

```text
32 字节 = 8 个 32 位 word = 256 bit
line_base = offset & ~31
lane = offset[4:2]                # 第几个 32 位 word，0~7
byte_in_word = offset[1:0]        # CPU 数据接口已经送对齐字地址
```

例如 `0x80000024`：窗口偏移是 `0x24`，行基址 `0x20`，word lane 是 1。读返回 256 位后右移 `32*1` 位，低 32 位就是该 word。

**地址单位不能想当然**：CPU/适配器端使用字节偏移，HMIC_S 的 28 位原生地址单位为 32 位 DDR 字；桥用 `hold_addr[29:2]` 转换。若把字节地址直接当原生地址，下游访问会偏移 4 倍。

## 18.2 先写一个简单的互斥仲裁器

取指和数据端都可能同时请求 DDR，但下级只处理一笔。最简单的安全设计是：

```text
IDLE：选择一个端口；只有被选者能握手。
SEND：保存地址/类型/数据/写使能，保持 req_valid 直到下级 ready。
WAIT_RSP：保持 owner 和 lane，等待下级响应。
返回对应端口的响应，并保持到 CPU 接收。
```

项目用 `prefer_i` 轮转选择，空闲时周期性翻转偏好，避免组合地让一个端口的 ready 依赖另一个端口的 valid/地址。若当前偏好的端口没有请求，另一个端口可能多等一个周期；这是一种控制路径与吞吐的取舍，不是两端各自并行发到 DDR。

在请求被接受时捕获 `owner_i`、`lane`、下级地址、写数据和 strobe。之后不再读取 CPU 当前地址来解释旧响应：等待期间 CPU 端可能已准备了其他信号。

## 18.3 数据写：把 4 个 strobe 放进 32 个 lane

项目用：

```systemverilog
req_wdata <= {8{d_req_wdata}};
req_wstrb <= {28'b0, d_req_wstrb} << {d_req_addr[4:2], 2'b0};
```

`d_req_wdata` 已经由 CPU 按 word 内 byte 位置移好。复制 8 份后，每个 32 位 lane 都有同样的字；只有 `req_wstrb` 对应的 4 位可能被使能，其余 byte 被屏蔽。例如 word lane 1、word 内写字节 2：

```text
CPU wstrb = 0100
256 位总线上对应 byte 序号 = 1×4+2 = 6
req_wstrb = 1 << 6
```

必须同时测试所有 4 个 word 内 strobe 位以及 8 个 word lane；若只测试整字写，很容易漏掉移位单位写错的问题。数据读则根据保存的 lane 对 256 位响应右移并取低 32 位。

## 18.4 指令取两字，恰好跨 32 字节边界怎么办

CPU 一次要返回 PC 与 PC+4 两个指令字：

```text
PC lane=6：同一行含 word 6、7，一次外部读取即可。
PC lane=7：第一条是当前行 word 7，第二条是下一行 word 0，需要两次读取。
```

适配器在第一次读完后保存第一条，若 lane=7、未到窗口末端且第一行未出错，地址加 32，设置 `second_line`，再次进入 SEND；第二次响应把低 32 位放进指令响应高半部。两个错误位要分别设置，不可将第二次出错误标到第一条。

末端地址 `0xbffffffc` 的第一条仍属于窗口，但 PC+4 越界；项目用 `last_word` 表示这种情况，返回第一字并标记第二字错误，不让地址截断回到 `0x80000000`。测试应分别覆盖 lane 6、lane 7、窗口末字、第一行错误和第二行错误。

## 18.5 什么时候响应必须保持

`i_rsp_valid/d_rsp_valid` 是面向 CPU 的响应。CPU 可能暂时不给 ready，例如队列满了。无论下级内部状态是否已经回到 IDLE，适配器在对应响应未被接收前都应保持响应数据和错误位稳定，不接收新的冲突请求。

在项目代码中，`IDLE` 选择新请求还要求两个响应 valid 均为 0。这样简化了一个响应缓冲的生命周期；同样可能有一拍气泡，先以正确性和时序可控为优先。

## 18.6 为什么不能把两组时钟直接接在一起

CPU 时钟与 DDR 控制器的 UI 时钟不一定同相、同频。若 CPU 域一拍同时改变地址和 valid，UI 域直接采样，可能遇到亚稳态或采到不同事务的混合数据。

项目采用 **bundled-data toggle mailbox**：

1. CPU 域在接收请求时，把地址、方向、256 位写数据及 32 位 strobe 存入 holding registers。
2. CPU 域翻转 `req_toggle`，并在收到确认之前保持这些数据稳定。
3. UI 域把 toggle 经同步器传入；看到同步后的新 toggle，读取稳定的数据并发给控制器。
4. UI 域完成后保存响应数据和错误，再更新 `ack_toggle`。
5. CPU 域同步 ack，确认它追上请求 toggle 后，采样响应并给上游一个保持型响应。

一次最多一个邮箱事务，因而没有 tag 队列来匹配多个在途请求。**宽数据不是把每一位各自接一个同步器就安全**：其稳定时间和跨域数据路径必须受约束；只同步 toggle 并把所有其他跨域路径设为 false path 会漏掉实际的时序要求。

## 18.7 为什么两侧需要共同复位

如果只有 CPU 域复位，`req_toggle` 可能回到 0，而 UI 端仍记得旧的 ack=1；两边会把残留状态误认为一个新请求或完成。项目要求 `reset_n` 同时作用于桥与控制器，并在各时钟域同步释放。

复位只是一个协议起点，还要测试在请求未完成时触发公共复位，以及 UI 时钟暂时停住。项目对 CPU 域和 UI 域分别设超时器；发生超时后把故障锁存，不能立刻复用邮箱，因为迟到的下级响应可能被错认成下一笔完成。只有按设计执行公共复位才能恢复。

## 18.8 这不是普通 AXI 的全部通道

项目针对 HMIC_S 的精简接口：没有普通 AXI 的 WVALID、B 响应和 RREADY。写通道需要在 AW 之前准备并保持写数据/写使能，直到 WREADY；读之前必须预留保存空间，因为无法用 RREADY 回压。

桥状态机有 `IDLE/AW/W/AR_R`：

- 写请求先进入 AW。如果地址与数据同拍被接收即可完成；地址先接收则转 W 等数据接收。
- 读请求在 AR_R 中发地址，记录 `ar_sent`，等待 `RVALID`；允许地址接受与响应在同拍的情况。
- 检查返回 ID/LAST；发生错误、校准丢失或超时后锁存 fault 并返回错误。

这里的写完成表示控制器接受写数据，不是已经测量到物理 DRAM 长期保存。不要把这个专用桥直接接到任意标准 AXI slave，也不要假设其他 IP 有完全相同的信号/握手；移植时须按 IP 手册重做适配与验证。

## 18.9 板级顶层、时钟与约束

默认 [qinglong_fpga_top.sv](../rtl/qinglong_fpga_top.sv) 是原始 27 MHz 起步封装，低有效 reset 经同步释放；GPIO 低 8 位接 LED，完成时显示退出状态，DDR 输入固定禁用。真实 DDR 板级顶层还必须连接厂商 IP、参考时钟、复位及所有 DDR 引脚。

对于这套项目记录中的板卡，DDR IP 采用 125 MHz UI；CPU 的 PLL 是另一条时钟路径。设计约束不能简单把所有 CDC 路径掩盖：同步器异步输入和 bundled-data 路径需分别处理，参考 [DDR 接入报告](../docs/板载DDR3接入与验证.md) 与对应工程约束。不同板卡/器件的 DQS、引脚、电压和 PHY 参数必须重新依据手册配置。

## 18.10 先仿真协议，再检查物理工程

在第 14 章建立的 WSL **隔离副本**中：

```bash
bash scripts/test_ddr.sh
```

脚本分别运行三组 CPU/UI 异步时钟比例的桥测试，再构建 DDR 自检固件，并在启用 DDR 的 SoC 模型执行。它会写 `build/ddr-tests` 等目录，因此不要和其他固件目标在同一目录并行运行。本次撰写时在独立副本运行通过：三组桥测试各报告 656 项检查，SoC 仿真输出 `DDR PASS data16KiB byte halfword address-lines edge execute` 并以 0 退出；链接器提示固件 LOAD 段具有 RWX 权限。这只是模型仿真，不是 DDR 板测。

建议自己写或核查下面的独立场景：

```text
请求 valid 先出现，下级 ready 延迟：地址和写数据持续稳定。
CPU 响应 ready 延迟：响应 valid/data/error 不变化。
全部 byte lane 的写使能；读回非目标字节不变。
I/D 同时请求：均最终获得服务，响应不串线。
lane 7 跨行、窗口末字、第二行错误：两个字的结果与错误分别正确。
未校准、校准丢失、返回 ID/LAST 错误、UI 时钟停止：返回错误并锁存故障。
事务中公共复位：两域重新对齐，不把旧响应当作新请求。
CPU 在 DDR 写入指令、FENCE.I 后执行：检查结果和错误路径。
```

仿真里的 DDR 模型不等同于芯片的模拟校准和物理时序。真正上板还需 IP 生成日志、引脚/电压审核、完整 PDS 静态时序、位流与固件哈希、上电校准和串口自检，并明确是否做过长时间/全容量/温压测试。

## 18.11 从这个实现迈向 Cache

当前适配器一次从 DDR 读取 32 字节，但读完后没有保留可重用 cache line；下次读取同一地址仍需再次访问下级。这与“用整行作为总线事务”不同于“有 Cache”。

如果以后增加两路组相联 Cache，应在 CPU 与这里的下级事务接口之间设计命中、填充、替换、写策略和 MMIO 绕过；还要定义 `FENCE.I`、写入后执行、DMA 一致性和错误传播。补齐这些功能并验证，才可以讨论是否满足赛题的 Cache 目标。
