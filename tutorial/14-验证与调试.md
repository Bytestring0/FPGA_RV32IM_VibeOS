# 14. 验证：先找到第一条出错的指令

当 CPU 输出了 `boot OK`，你知道它执行了某些指令、访问了某些内存并输出了字符；你不知道它是否能正确处理每一种指令，也不知道预测失败时是否偷偷执行过错误路径上的 Store。验证的目标不是“跑出一个漂亮结果”，而是针对每条关键约束设计会暴露错误的观察。

这章分两件事：先在不覆盖原有工作成果的副本中运行现有回归；然后解释每一层测试到底检查了什么、失败时从哪里下手。

## 14.1 先建立隔离副本

项目的 `make smoke`、ISA、异常测试和 CoreMark 会共用并覆盖 `build/firmware.hex`。PDS 同步脚本还会覆盖生成源码、工程设置和根目录固件。请先备份有价值的数据，不要在唯一工作目录中并行运行这些目标。

下面以 WSL Ubuntu 为例；工作区在 `/mnt/d/FPGA/RiscV`，如果你的路径不同先修改 `src`：

```bash
src=/mnt/d/FPGA/RiscV
work=$(mktemp -d /tmp/qinglong-tutorial-check-XXXXXX)
printf '隔离副本：%s\n' "$work"
cp "$src/Makefile" "$work/"
cp -a "$src/rtl" "$src/sim" "$src/scripts" "$src/sw" \
      "$src/tests" "$src/third_party" "$work/"
cd "$work"
```

`mktemp` 新建目录，不清理、覆盖原有项目。把打印的路径记下来；此目录是实验产物，需保留还是手动清理由你决定。确认 `third_party/coremark` 和 `third_party/riscv-tests` 可读取；如果 WSL 下复制出现链接或权限错误，先检查实际路径和目录内容，不要把失败忽略。首次缺依赖时可在隔离副本运行 `make deps`，它需要网络并检出脚本指定的第三方版本。

确认工具：

```bash
command -v make g++ python3 verilator riscv64-unknown-elf-gcc
```

项目默认使用 `riscv64-unknown-elf-` 前缀，但编译参数明确指定 RV32/ILP32。赛题文字写 `riscv32-unknown-elf-gcc`；若提交时要求工具链名称或版本严格一致，应向主办方确认并记录实际版本，不要只因为生成 RV32 代码就自行断言满足所有形式要求。

## 14.2 先检查能否编译，再运行短程序

仍在隔离副本：

```bash
make lint
make smoke
```

`lint` 检查 SystemVerilog 结构与部分可疑写法；本项目 `-Wno-fatal` 会让警告不直接变成失败，因此退出码 0 不代表没有警告。查看警告内容，确认是否是已理解的工具提示、宽度问题或真正的多驱动。

`smoke` 编译 C 固件、转换为镜像、编译 Verilator SoC 模型并运行。它涉及启动、内存、循环、UART 快速输出和退出码。失败时先问是：

1. 工具不存在/编译链接失败？看编译命令与第一条错误。
2. 模型启动但超时？看 PC、总线握手、复位/固件路径。
3. 输出错误或退出码非零？先对照固件反汇编找到第一条异常行为。

不要只看到最后的 `make: *** Error`；真正的错误通常在前面的工具输出中。

## 14.3 跑完整回归

```bash
make check
```

项目 [Makefile](../Makefile#L24-L26) 顺序运行 `smoke isa traps interrupts dual-stress differential uart uart-soc`。不同目标覆盖：

| 目标 | 主要观察 | 不能推断什么 |
| --- | --- | --- |
| `smoke` | 固件启动、RAM、简单运算和快速 UART | 全 ISA、物理串口 |
| `isa` | 上游 RV32 指令定向用例 | 全部配置与所有异常组合 |
| `traps` | 异常与 CSR 汇编定向测试 | 所有可能中断交错 |
| `interrupts` | 定时/软件/外部中断用例 | 任意异步输入 CDC 安全 |
| `dual-stress` | 双发射与相关专项 | 所有随机组合 |
| `differential` | 随机等待下按退休顺序与软件模型对照 | CSR 与所有外设均被独立建模 |
| `uart` | TX 模块波形/时间检查 | 板上引脚、电平、电缆 |
| `uart-soc` | SoC 经真实 UART TX 输出 | FPGA 布线时序 |

ISA 脚本跳过 `ma_data`，因为该测试要求硬件直接完成不对齐数据访问，而本核心选择精确异常；应单独看 trap 测试，不能把跳过说成该测试通过。测试数量取决于本地上游源与版本，应查看本次日志，不要复制历史数字充当自己的结果。

本次撰写时在 WSL 临时副本运行 `make lint` 和默认参数的 `make check`，进程成功退出，ISA 输出 70 项通过；lint 有宽度等警告，并不代表警告被消除。这次验证不是 FPGA 时序或上板验证，实际运行时以你自己的副本与日志为准。

`make differential` 依赖先生成 ISA 的 `build/isa/*.bin`；单独执行时应先 `make isa`。不同参数、工具、源版本的结果必须分开记录。

## 14.4 差分测试为什么比只看最终值强

项目 [sim/core_main.cpp](../sim/core_main.cpp) 有一个独立的软件顺序参考模型。它从内存读取下一条指令，维护自己的 PC、32 个寄存器和内存，并在 DUT 退休时检查：

```text
参考 PC   == DUT retire_pc
参考指令  == DUT retire_insn
参考 rd   == DUT retire_rd
参考结果  == DUT retire_data
```

两条同拍退休时，先对照较老的第一条并更新参考状态，再处理第二条。它还检查“第二口有效但第一口无效”等错误，并随机延迟请求/响应、检查数据请求在背压期间稳定。

因为参考模型独立逐条执行，一旦首条错误出现，报告会含指令序号、lane、参考/DUT PC、机器码、rd 和数据。这通常比跑完几百万拍再比较最终 `x5` 更容易定位。例如 `x5` 曾被错误写入后又被后续指令覆盖，最终值可能看起来正确，但退休差分会在错误的那一条就停下。

参考模型也有边界：源码明确说 CSR 结果由单独 trap 测试负责；某些 MMIO 访问不能像普通 RAM 一样独立推导。覆盖边界要如实写进报告，不能称它为完整形式验证。

## 14.5 如何从第一条错误逆推

假设错误报告在 `PC=0x100` 的 ADD，参考值是 12、DUT 值是 9。按这个次序：

1. 用 `objdump -d` 查 PC 和机器码，确定 rs1/rs2/rd 和邻近几条指令。
2. 在参考轨迹中找到这两个源寄存器最近的较老写者。
3. 打开波形看消费者的 EX PC/valid、`x_a/x_b`、最终 `a/b`、相关 `forward_*`、MEM/WB rd/result。
4. 如果之前有 Load，检查响应何时握手、`m_finish` 与 `hazard` 是否阻止过早推进。
5. 如果发生长 stall，检查 WB 旁路消失前是否保存了最新操作数。
6. 如果发生双发射或交换，记录程序年龄、物理通道和两次退休顺序。
7. 修复后先重跑最小失败用例，再跑完整回归和参数组合。

调试过程中不要先用 RTL 当前输出改参考值；参考应来自 ISA 语义、手算或独立模型。保留原始 seed/固件/源码哈希，才能在修改前后证明复现和修复。

## 14.6 波形上有哪些最有用的信号

以一条 Load 失败为例，不必一开始把全部内部信号都加进波形。先按时间排：

```text
clk、rst、retire_valid/pc/insn/rd/data、trap_valid/pc/cause/value
x_valid/x_pc/x_dec、m_valid/m_pc/m_sent/m_addr、w_valid/w_pc
hazard、x_go、m_finish、m_ready、mem_trap
 d_req_valid/ready/addr/write/wdata/wstrb
 d_rsp_valid/ready/data/error
```

然后沿着“接受请求→等待→响应→结果→退休或陷阱”寻找第一次偏离预期的沿。某个总线字段有 X 时，先确认它在对应 valid 时是否应该有效；无效气泡中的旧值不一定是 bug，有效 Store 的地址含 X 则是严重问题。

取指故障再加 `f_pc/q_pc/q_valid/q_killed/fetch_count/redirect`；双发射加 `pair_issue/pair_swapped/x_swapped/m_swapped` 和两个退休口。波形记录方式和激活开关需以你使用的仿真器、项目测试入口为准，不应假设每个现成目标默认产生 VCD。

## 14.7 参数对照是测试，不是性能数字的自由拼接

可在隔离副本顺序运行，例如：

```bash
make check DUAL_ISSUE=0 PREDICT=0 LOAD_BYPASS=0 EARLY_LSU=0
make check DUAL_ISSUE=1 PREDICT=1 LOAD_BYPASS=1 EARLY_LSU=1
```

完整回归耗时可能较长；参数在 Makefile 中传给仿真构建，PDS 板级是否采用同样值要另核对 RTL 参数与构建产物。比较时保存每组完整命令、退出状态、日志、固件、源码版本、工具版本；不要取 A 配置的功能测试、B 配置的资源、C 配置的主频拼成一个“验证过”的成绩。

预测或双发射开关改变周期，不应改变相同测试的架构结果；有外部定时中断的测试则需确保中断刺激方式可比较，不能假设不同周期时间下每条指令边界完全相同。

## 14.8 从仿真到板上还缺什么

仿真可验证特定输入和模型中的行为；综合、布局布线和板测分别涉及 FPGA 资源映射、约束、时钟、引脚、电平、上电复位和实际设备。`make check` 成功并不等于时序闭合或板卡运行成功。
