# 16. 核心组装施工手册：真的开始写 `my_core`

前面几章按主题解释了核心的关键部件。现在把它们放回同一张施工图里：假设你面前是一个空的 `my_core.sv`，应该按什么顺序声明信号、接模块、写状态更新、跑测试，才能一步步得到具备青龙行为的核心？

先说清楚范围：本章提供的是**从模块到系统的实施路径和关键代码骨架**。仓库 [rv32_core.sv](../rtl/rv32_core.sv) 是完整实现的逐行对照对象；文中的片段刻意省略了一些信号、两路和异常处理，不能拼接后直接当作完整工程。教程中的独立实验可以运行，但目前没有额外提供一套与青龙全部功能及逐周期行为等价的第二份 CPU 源码。

这不是要求你先看完 654 行再“理解”——下面每一节规定一个要写的接口、具体条件、通过标准和在原文件中的位置。遇到一个阶段失败时，不继续叠功能。

## 16.1 准备一个不影响原项目的工作区

在你自己选定的位置创建新项目 `my-rv32`，不要覆盖仓库 `rtl/`：

```text
my-rv32/
  rtl/
    my_pkg.sv
    my_decode.sv
    my_alu.sv
    my_predictor.sv
    my_divider.sv
    my_csr.sv
    my_core.sv
    my_soc.sv
    my_uart_tx.sv
  sim/
    ...你的测试台...
  sw/
    start.S
    link.ld
    smoke.c
  logs/
```

建议使用 Git 做版本记录；每个里程碑留一个提交或保存目录及测试日志。写项目时可以先直接实例化仓库单元模块，等系统最小路径跑通后，再逐个替换成自己的实现并回归。这样可以把“我的译码器错了”和“流水线接线错了”区分开；但最终能否说自己独立实现，取决于你实际写了什么，不能把直接使用原模块当作自写。

## 16.2 第一份文件：冻结 core 端口和参数

使用第 4 章列出的指令/数据请求响应端口，补齐中断、退休和 trap 接口。与项目保持一致有几个实际好处：

1. 可以写同一份总线模型给原核心和你的核心使用。
2. 能复用按退休比较的测试思路，而不是深入每个核心的内部数组。
3. 将来可以在同样的 SoC 连接点替换核心。

还要给 `RESET_PC`、预测、双发射、Load bypass、early LSU 和乘法流水参数保留位置。**占有一个参数名不表示功能已实现**：初期若不支持某配置，就在仿真/构建时明确拒绝或固定设置，避免静默接受并运行错误模式。

检查点：先让只含端口的空壳能编译，所有输出给确定的默认值；此时绝不能对外发请求。保留 `valid` 驱动的唯一所有者，别让连续赋值和 `always_comb` 同时驱动同一信号。

## 16.3 第二份文件：定义每条指令携带什么

一条指令需要从前端到退休，因此每个阶段都要明确字段所属。下面是清晰但不强调面积的结构化方案：

```systemverilog
typedef struct packed {
    logic [31:0] pc, insn, predicted_next;
    logic fetch_error;
} fetched_t;

typedef struct packed {
    fetched_t fetch;
    decode_t dec;
    logic [31:0] rs1_value, rs2_value;
} execute_t;

typedef struct packed {
    logic [31:0] pc, insn, address, result, store_value;
    logic [31:0] cause, tval;
    logic [4:0] rd;
    logic [2:0] funct3;
    logic write_rd, load, store, exception;
} memory_t;
```

这是教学时用的结构示意，不是项目的直接替换代码：完整实现还需要串行、CSR、乘除、双发射等字段。PDS 版本对结构体端口有兼容要求，所以项目某些模块通过固定宽度的 packed 位向量传结构，再在内部转换；先使用你目标工具支持的写法。

现在就为每个字段写一行“谁产生、何时捕获、何时无效”：

| 字段 | 产生 | 捕获 | 失效 |
| --- | --- | --- | --- |
| fetch PC/insn/error | 总线响应 + q 上下文 | 响应接收且未 kill | 前端 flush 或队列 pop |
| EX 控制/操作数 | 队首译码和读口 | ID 真正发射 | EX 推进、较老 trap 或 reset |
| MEM 地址/结果/cause | EX | `x_go` 且 MEM 可接收 | `m_finish` 后替换或气泡 |
| WB PC/rd/result | MEM 最终结果 | `m_finish` 且允许正常退休 | 下一沿或 reset |

记住 `valid=0` 时 payload 可以是旧值；所有写寄存器、发总线请求、更新 CSR 和退休信号都必须受相应 valid 和异常条件保护。

## 16.4 第三个里程碑：先只接一条指令

保持一次最多执行一条指令，先把所有流水重叠关掉：

```text
RESET → 请求 PC → 等指令响应 → 译码和算结果
      → 如有 Load/Store，发请求并等响应
      → 产生一次退休 → 更新 PC → 请求下一条
```

只实现 ADDI/LUI/ADD/SUB 时，就用第 1、2 章的机器码程序检查 `PC/rd/data`。然后分次加分支、跳转、访存。为了减少变量，初始总线模型先固定一拍响应；接着让 ready 和响应分别随机等待。

即使是多周期核心，依然要保存：被接受取指的 PC、访存宽度和目标 rd、访存的原地址；不要等到响应回来再去看“当前译码”的字段。遇到错误时，暂时可以在测试台明确报告未支持，但不能把这个阶段宣称为已支持精确异常。

检查点：`addi x5,x0,7; addi x6,x5,-3` 依次退休为 `(PC=0, rd=5, data=7)`、`(PC=4, rd=6, data=4)`，且每条恰好退休一次。测试时还必须保证固件不会继续落入未经定义的全零内存；可以使用程序末尾循环或清晰的结束设备。

## 16.5 第四个里程碑：拆开 EX、MEM、WB

现在让一条指令进入 MEM 后，下一条可以占据 EX。先不做旁路：若后续指令读了任何尚未提交的寄存器，就阻塞它；让结果容易检查。需要完整可运行代码时，先看 [第 19 章的单发射流水线](19-亲手搭单发射流水线.md)，再回来按这里的步骤把它扩展到项目功能。

写控制之前，先用文字定义三个事件：

```text
m_finish：当前 MEM 指令本沿能产生结果/异常并离开。
x_go：当前 EX 指令本沿可以进入 MEM。
id_issue：当前队首本沿可以进入 EX。
```

然后按倒序写 ready：

```systemverilog
m_ready = !m_valid || m_finish;
x_ready = !x_valid || x_go;
```

对于自己的保守第一版，`m_finish` 在 ALU 时可立即为真，Load/Store 必须等对应响应；`x_go` 要求 MEM ready、没有依赖和所有多周期条件满足；`id_issue` 要求队首 valid、EX ready 且不是 flush/serial 阻塞。等你加入 precise trap 才能确定完整公式；原项目的最终公式在 [381–443 行](../rtl/rv32_core.sv#L381-L443)。

**必须画同拍替换**：沿前 MEM=旧 A、EX=新 B；若 A 完成本沿且 B 可推进，则沿后 MEM=B。若 B 无效，沿后 MEM 应为空。你可以从这种模板开始：

```systemverilog
if (m_ready) begin
    m_valid <= x_go && !older_trap && !interrupt_taken;
    if (x_go) begin
        m_pc <= x_pc;
        m_insn <= x_insn;
        // 后续把所有需要随指令移动的字段一一写在这里
    end
end
```

该片段依赖尚未给出的完整声明和控制，不能单独编译。项目相应代码是 [611–632 行](../rtl/rv32_core.sv#L611-L632)。对照时不要漏掉 `m_sent`、异常信息、CSR、乘法输入和辅助通道载荷。

WB 同样在 `m_finish` 时捕获结果；WB 的有效位每拍重算，避免同一条指令连续退休。正常返回与异常发生都应有独立观测。先对连续独立 ADDI、后接依赖 ADD、长延迟 Load 分别画出每沿的 x/m/w valid；确认无重复后才加吞吐优化。

## 16.6 第五个里程碑：把数据相关从暂停改成旁路

先在测试台记录消费者希望用到的两个源寄存器以及最近的较老写者，再按以下顺序实施：

1. WB→ID 读口旁路：同拍读写同地址时读到新值。
2. WB→EX 旁路：EX 不必一直等到寄存器数组写回。
3. MEM→EX 普通 ALU 旁路：较新的 MEM 结果覆盖更老的 WB 结果。
4. Load 成功响应旁路：只有结果真正可用且没有 trap，消费者才允许前进。
5. 补充长暂停时的操作数保持。

写测试时用三个不同值而不是重复的 1：

```asm
addi x5,x0,11
addi x5,x0,22
add  x6,x5,x5       # 正确结果 44；读到旧写者则是 22
```

还需在 Store 数据、分支比较、JALR 目标上测试旁路；把旁路只接到 ALU 输入而没接分支/地址/Store 会漏错。EX 暂停时如果某个操作数从 WB 旁路获得新值，项目把该值保存回 `x_a/x_b`；见 [601–605 行](../rtl/rv32_core.sv#L601-L605)。

最终的前置编号比较与完整两通道优先级参考 [145–179](../rtl/rv32_core.sv#L145-L179)、[245–275](../rtl/rv32_core.sv#L245-L275)、[357–379](../rtl/rv32_core.sv#L357-L379)。先写易读版本，再根据时序报告考虑是否采用相同优化；每次只改一类逻辑并复跑测试。

## 16.7 第六个里程碑：写前端队列并单发射

这一里程碑先不加真实预测，约定 `predicted_next=PC+4`。队列容量四项，每项保存 PC/insn/error；加预测后再加 predicted_next 和预译码 metadata。

随教程提供的 [fetch_queue.sv](examples/08-fetch-queue/fetch_queue.sv) 是一个简化的四项队列：

- 每拍弹出 0、1、2 项；环境保证不超过当前 count。
- 可请求推入 1 或 2 项；`push_ready` 根据沿前空位保守判断。
- 同拍先在概念上 pop，再把新项 append；flush/reset 优先清空 count。
- 它不处理总线、取指在途请求或预测，不是项目完整前端。

在项目根目录运行随机参考模型测试：

```powershell
iverilog -g2012 -s fetch_queue_tb -o "$env:TEMP\fetch_queue.vvp" `
  tutorial/examples/08-fetch-queue/fetch_queue.sv `
  tutorial/examples/08-fetch-queue/fetch_queue_tb.sv
if ($LASTEXITCODE -ne 0) { throw '编译失败' }
vvp "$env:TEMP\fetch_queue.vvp"
if ($LASTEXITCODE -ne 0) { throw '测试失败' }
```

本次运行得到 `PASS fetch_queue: 5000 cycles, 148 flushes, 871 simultaneous pop/push`。不同仿真器随机种子/实现可使后两个数不同；重点是测试确实覆盖且所有条目按序相等。

再增加一个在途取指状态 `q_valid/q_pc/q_killed`：请求被接收保存 PC；响应被接收时，未 killed 才把一或两条推入队列；重定向时队列清空且在途请求 killed。第 7 章讨论了同拍消费旧响应与接收新请求的优先级，必须单独写定向测试。

对照项目时不要直接把教学队列加到 `rv32_core` 里：项目为了缩短路径使用预译码和静态索引比较，并和 q、redirect 状态共同实现队列。先理解 [541–578 行](../rtl/rv32_core.sv#L541-L578) 的压缩、追加和最终清空优先级，再决定自己的写法。

## 16.8 第七个里程碑：连接访存与精确异常

先完成 `EARLY_LSU=0` 的保守 MEM 请求，再考虑提前到 EX。无论选择哪一种：

```text
指令有效且没有本地异常 → 构造请求
valid && ready → 这一笔被接受（标记 sent）
等待期间 → 不再重复发同一笔
响应 valid && ready → 得到值或错误
成功 → 允许该指令正常退休；错误 → 产生 trap，禁止错误写回
```

创建一个计数型设备模型，每次 Store 请求真正握手就计数。让较老 Load 错误、较年轻 Store 在后面等待；断言设备计数为 0。然后交换年龄，再验证已经合法发生的较老 Store 不能被年轻异常“抹掉”。

复核两个地址：外部请求地址按字对齐，异常 `mtval` 保存原始有效地址。LB/LH/LBU/LHU 要在响应后取 lane 和扩展，SB/SH 的数据和 wstrb 要一起移位；详细手算在第 9 章。

## 16.9 第八个里程碑：加入双发射，但一次只扩展一种组合

先让两条简单 ALU 配对，禁止同组 RAW/WAW；核对同拍两个退休口。然后允许 A 用完整通道、B 用辅助 ALU；最后增加 A 在辅助、B 在完整通道的交换。

开始写之前把下面这张表放进测试计划：

| 模式 | 物理主通道 | 物理辅助 | 第一退休 | 第二退休 |
| --- | --- | --- | --- | --- |
| 普通 | 年长 A | 年轻 B | A | B |
| 交换 | 年轻 B | 年长 A | A | B |
| 普通且 A trap | A 出错 | B | 两者不正常退休 | 无 |
| 交换且 B trap | B 出错 | A | A 正常退休 | 无 |

这里描述的是这两种具体场景，不意味着任何异常都可以简单套用表格。检查实际的 `x_exception/mem_trap` 来源和串行/配对约束。

真正实现时 `x_swapped` 必须随组到 `m_swapped`，WB 用它选择 PC、insn、rd、result 的输出位置。只交换数据不交换指令字或目的编号，会让算术值看似正确而退休记录完全错位。对照 [579–645 行](../rtl/rv32_core.sv#L579-L645)。

## 16.10 第九个里程碑：CSR、中断和乘除分别并入

建议每接入一种单元就进行一次全回归，而不是一次连好：

- **CSR**：读端组合、写端在合适提交阶段生效；非法地址/只读写产生异常。先在无中断情况下测试 CSR 指令，再接 trap。
- **trap**：保存 PC、cause、value，禁止出错指令副作用；从 `mtvec` 重定向。验证较老/较年轻指令的精确状态。
- **中断**：pending 时停止普通新发射并排空，在明确的队首边界接收；MRET 后恢复。外部输入先同步。
- **乘法**：对四种符号组合使用独立宽位参考比较，验证后再采用项目的分片 DSP 优化。
- **除法**：启动一次，忙时保留上下文，done 遇 stall 保存结果，较老 trap 时 cancel。测试除零、溢出和负余数。
- **预测器**：从顺序预测开始，接 BTB/历史/RAS 后，确保错误预测永远由 EX 纠正。预测命中率是性能指标，不是功能判定依据。

这些单元的详细行为在第 11、12 章；与 SoC 结合的输出以第 13 章和实际平台地址表为准。

## 16.11 一张最终集成检查表

逐项打勾时把用例与日志位置写下来；“源码有这个信号”不是通过条件。

```text
[ ] reset 后没有无效请求/退休；从 RESET_PC 取到正确首条指令。
[ ] x0 永远为 0，未初始化 x1–x31 不被软件依赖。
[ ] 任意请求 backpressure 下数据端载荷保持；单笔至多接收一次。
[ ] 指令请求接受前可取消；接受后返回的错误路径响应被正确丢弃。
[ ] 取指返回两项时 PC、机器码、错误位、预测和元数据保持配对。
[ ] EX/MEM/WB 暂停、同拍替换、flush 时没有丢指令或多退休。
[ ] RAW/WAW、最近写者优先、长 stall 的旁路值保存正确。
[ ] 对齐、字节使能、符号扩展、总线错误和较老 trap 抑制 Store 正确。
[ ] 双发射正常与交换配对、异常年龄和退休顺序正确。
[ ] CSR、同步异常、机器态中断、MRET 和系统串行正确。
[ ] 乘除全部边界、取消及与等待交互正确。
[ ] 预测错路径不能提交副作用；FENCE.I 后前端正确恢复。
[ ] 指令/随机总线差分、异常和 UART 回归在目标配置下通过。
[ ] FPGA 引脚、时钟、时序、固件、位流和板上证据另行闭合。
```

对照清单完成后，仍需留意两个层次：你写的是与项目功能一致的实现，还是与它**逐周期相同**的微架构？前者可用退休流和总线契约比较；后者还要对照每拍内部状态、同拍事务优先级和所有参数。资源/主频则必须用目标 FPGA 构建实测。
