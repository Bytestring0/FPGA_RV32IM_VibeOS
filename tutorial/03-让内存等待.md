# 3. 内存不能立刻回答怎么办

上章假定地址一变化，内存数据马上出现。请想象你去柜台取件：你先把取件码交给工作人员；工作人员接收后，需要时间找包裹；找到后告诉你取件成功。你不会在刚递出取件码时就说“我已经拿到包裹”，也不会每等一秒就重新下一个订单。

CPU 访问同步 RAM、外设或者 DDR 同样需要区分这些事件。这一章先单独做一个等待 RAM，再讨论如何把这种接口接进 CPU。

## 3.1 `valid` 和 `ready` 分别代表什么

一条请求包括地址、是否写、写数据和字节选通；请求发送方和接收方还有两根控制线：

```text
req_valid：发送方说“我现在提供的是一个有效请求”。
req_ready：接收方说“这个上升沿我可以接收请求”。
```

只有两者在**同一个上升沿**都是 1，才算请求被接收。这次接收称为一次握手。假设：

| 时钟沿前 | valid | ready | 发生什么 |
| --- | ---: | ---: | --- |
| 第 1 个沿 | 1 | 0 | 没接收；请求仍在等待 |
| 第 2 个沿 | 1 | 0 | 仍没接收 |
| 第 3 个沿 | 1 | 1 | 这一个沿接收一次请求 |
| 第 4 个沿 | 0 | 0 | 已接收过，发送方不应重复发同一请求 |

本章示例约定：请求未被接受时，发送方保持地址、数据和控制稳定。项目**数据端口**同样要求稳定；项目取指端在接受之前允许重定向取消，不能给所有端口机械套同一条断言。它也不是可直接当 AXI 使用的接口。

## 3.2 响应还有另一组握手

接收请求后，RAM 可能几个周期后才把响应放到输出：

```text
rsp_valid：RAM 说“响应已经准备好”。
rsp_ready：CPU 说“我在这个沿可以接收响应”。
```

如果 `rsp_valid=1` 而 `rsp_ready=0`，RAM 不能下一拍就把数据撤掉或换掉。它要一直保持响应有效、数据和错误位稳定，直到 `rsp_valid && rsp_ready` 的上升沿。

因此一个完整访问至少涉及两个不同的事件：

```text
请求握手 → 等待若干周期 → 响应握手
```

“请求被接收”和“结果可以使用”不是同一件事；若 CPU 在请求接收时就让 Load 写回，它可能把上一笔的数据误当成本次结果。

## 3.3 运行等待 RAM

这一次我们不运行 CPU，先把存储器本身测清楚：

```powershell
iverilog -g2012 -s wait_ram_tb -o "$env:TEMP\wait_ram.vvp" `
  examples/03-handshake/wait_ram.sv examples/03-handshake/wait_ram_tb.sv
if ($LASTEXITCODE -ne 0) { throw '编译失败' }
vvp "$env:TEMP\wait_ram.vvp"
if ($LASTEXITCODE -ne 0) { throw '仿真失败' }
```

结果应包含：

```text
PASS wait_ram: 6 accepted requests
```

打开 [wait_ram_tb.sv](examples/03-handshake/wait_ram_tb.sv)，它顺序执行：

1. 地址 0 写 `0x11223344`。
2. 对地址 0 的第 2 个字节写 `0xaa`。
3. 读回，检查结果为 `0x11aa3344`。
4. 请求地址 64：超出这个 16 字 RAM，期望错误。
5. 请求地址 2：不是字对齐，期望错误。
6. 再读地址 0，确认前面的错误写没有破坏原值。

每次响应都被故意反压三个时钟，检查响应保持；另外记录请求握手次数应恰好是 6。测试台还有超时，如果双方一直等对方不会误报通过。

## 3.4 先搞清楚字节与字

RAM 数组一项是 32 位，也就是 4 字节。总线地址是**字节地址**。对于一个对齐字地址 0：

```text
字节地址      0      1      2      3
保存的值     44     33     22     11
合成 32 位值：0x11223344
```

RISC-V 的小端约定让低地址字节放在低位。我们要改地址 2 的字节为 `aa`，那么总线提供：

```text
对齐地址  = 0
wstrb     = 0100
wdata     = 00aa0000
```

`wstrb[2]` 为 1，告诉 RAM 只更新 `wdata[23:16]`。对应 RTL：

```systemverilog
for (int j = 0; j < 4; j = j + 1)
    if (req_wstrb[j])
        ram[req_addr[31:2]][8*j +: 8] <= req_wdata[8*j +: 8];
```

`[8*j +: 8]` 表示从第 `8*j` 位开始，向高位取 8 位。第 2 个 lane 是 `[23:16]`。循环中的非阻塞赋值都在同一沿生效，不是逐个占用四个周期。

## 3.5 看懂这个 RAM 的状态

打开 [wait_ram.sv](examples/03-handshake/wait_ram.sv)。这个教学模型只允许一个请求在途：

```text
空闲：pending=0，rsp_valid=0，req_ready=1
接收：req_valid && req_ready，保存结果并设置 pending
等待：递减 delay_left
响应：rsp_valid=1，直到 rsp_ready=1 才撤销
```

请求接收时写操作就修改 RAM；错误地址不触碰 RAM，但仍产生错误响应。示例的响应延迟是固定的，为了把状态看清楚；实际项目测试会引入不同等待时长。

`req_ready = !rst && !pending && !rsp_valid` 使它在响应被消费的同一沿不能接收下一个请求。这容易理解但吞吐较低。真实项目允许某些旧响应完成和新请求接收同拍发生，必须正确处理状态覆盖，不能仅修改这一行就声称支持。

复位会取消该示例中尚未给出的响应，但不清空 RAM；所以 testbench 先写再读，不依赖 RAM 初始内容。

## 3.6 如果把它接到 CPU，CPU 还要保存什么

试着改造上章的 `LW x3,0(x0)`。如果 CPU 进入等待时不保存指令的上下文，响应到来时就可能不知道结果应该写给谁。最简单的保守状态机：

```text
EXEC：计算有效地址并检查对齐；保存目的寄存器和访存类型。
REQ：保持请求内容，直到 req_valid && req_ready。
WAIT：等待 rsp_valid && rsp_ready，不重复发请求。
DONE：成功的 Load 写回保存的 rd；错误则走错误处理。
```

例如：

| 边沿 | 状态 | 事件 |
| --- | --- | --- |
| 1 | EXEC | 算出地址 0，保存 rd=3 |
| 2 | REQ | valid=1、ready=0，继续等待 |
| 3 | REQ | valid=1、ready=1，请求被接受 |
| 4～6 | WAIT | 尚无响应，不能写 x3 |
| 7 | WAIT | 消费成功响应，保存读回值 |
| 8 | DONE | 根据保存的 rd=3 写回 |

这只是一个容易理解的示意时序，不是项目逐周期波形。项目默认可在 EX 发请求、在 MEM 等待响应，而且允许更老/更年轻指令同时处于其他阶段；它需要更严格的年龄和异常控制。相关完整过程将在 [第 9 章](09-访存路径.md)实现。

## 3.7 两个容易被忽略的问题

**问题一：写请求已经被接收，后来响应报错，能保证内存没被修改吗？**

不能只从 CPU 的响应信号推断。必须由总线/设备契约明确错误与副作用的关系。这个教学 RAM 对非法地址先判断再写，因此错误写无副作用。其他外设若在产生错误前已发生不可撤销动作，需要系统级设计约定。精确异常也要求错误路径和年轻 Store 不提前产生不该有的副作用。

**问题二：响应有效但被反压，发送方可以先换数据吗？**

不可以。本示例直到响应被接受才清 `rsp_valid`，期间不更新响应寄存器；testbench 的三拍反压就是为了捕捉违反这个约定的实现。

## 3.8 动手实验

把 `delay_left <= 2` 改成 0，重新运行，结果仍应 PASS，只是等待时间不同。然后去掉 `rsp_valid` 的保持条件、让它只脉冲一拍，测试应该失败或超时；恢复原实现。

这里已经建立了后面需要的直觉：握手把事务分成接收和完成，CPU 必须保存上下文。在 [第 4 章](04-完整项目从哪里开始.md)，我们开始围绕真实项目设计接口和实现顺序，不再把它当作上章单周期 CPU 的简单续写。
