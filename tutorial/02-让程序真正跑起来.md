# 2. 让一个求和程序跑起来

上章的电路只会做加法，而且每次都走到下一条指令。它还称不上一个能执行普通程序的 CPU：没有循环、没有访问数据内存的方法。这一章我们给它补上这些最基本的能力，运行一个从 5 加到 1 的程序。

我们不会一口气实现全部 RV32I。实验只支持 `LUI`、`ADDI`、`ADD/SUB`、`LW/SW`、`BEQ/BNE` 和 `JAL`；不认识的指令或本模型发现的非对齐地址会停机，不会进入架构异常处理。数据读和指令读仍然是组合完成的。这些限制不是小细节，它决定了你不能拿这个实验去跑项目的完整固件。

## 2.1 先看程序要干什么

完整汇编是 [sum.S](examples/02-single-cycle/sum.S)，核心循环如下：

```asm
addi x1, x0, 0       # sum = 0
addi x2, x0, 5       # remaining = 5
loop:
    add  x1, x1, x2  # sum += remaining
    addi x2, x2, -1
    bne  x2, x0, loop
sw x1, 0(x0)
lw x3, 0(x0)
```

逐次经过循环时，`x1` 分别变成 `5、9、12、14、15`，`x2` 从 5 降到 0。随后把结果 15 写到数据内存地址 0，再加载到 x3。后面的指令还检查 `SUB`、相等分支、`JAL` 的链接地址以及被跳过的指令没有执行。

注意：这里测试台使用**独立的指令 ROM 和数据 RAM**。因此对数据地址 0 写入不会覆盖 ROM 中 PC 0 的指令。项目 SoC 则使用统一 TCM，并给核心提供分开的指令和数据访问端口；两种设计不能直接混为一谈。

## 2.2 运行并观察

在教程目录执行：

```powershell
iverilog -g2012 -s small_tb -o "$env:TEMP\small_cpu.vvp" `
  examples/02-single-cycle/small_cpu.sv examples/02-single-cycle/small_tb.sv
if ($LASTEXITCODE -ne 0) { throw '编译失败' }
vvp "$env:TEMP\small_cpu.vvp"
if ($LASTEXITCODE -ne 0) { throw '仿真失败' }
```

会看到 PC 多次在 `8、c、10` 间循环，随后经过 `14、18、1c、20、28、30、34`；`24` 和 `2c` 被分支/跳转跳过。最后应该有：

```text
PASS small_cpu: sum=15 stores=1 link=44
```

数值 44 是十进制，即 `0x2c`。`JAL` 在 PC `0x28`，写回的链接地址是本条指令 PC+4，而不是目标地址 `0x30`。

## 2.3 我们需要哪些硬件线

看 [small_cpu.sv](examples/02-single-cycle/small_cpu.sv) 的端口。与上章相比，多了：

```text
mem_addr   CPU 想访问的数据字节地址
mem_wdata  要写入的数据
mem_we     是否在本周期的上升沿写
mem_rdata  测试内存根据地址组合返回的数据
```

现在一条 LW 的数据路径是：

```text
指令中的 rs1 ─→ 读寄存器 ─┐
                          加法 ─→ mem_addr ─→ RAM ─→ mem_rdata ─→ 写 rd
符号扩展的 I 立即数 ──────┘
```

SW 则把 rs2 的值连到 `mem_wdata`，目标地址来自 rs1 与 S 型立即数之和。`mem_we` 只能在合法、已对齐、没有复位且没有停机时为 1；否则空闲或错误指令也可能在时钟沿意外写 RAM。

本实验只实现对齐的 32 位读写。测试 RAM 对越界写主动 `$fatal`，但 CPU 没有总线错误输入，越界读在测试环境中只是返回 0——它不是有访问错误处理的真实 CPU。

## 2.4 默认值为什么放在 case 前面

打开 `always_comb`，先看到：

```systemverilog
next_pc = pc + 32'd4;
result = 0;
write_rd = 0;
bad = 0;
mem_addr = 0;
mem_wdata = b;
mem_we = 0;
```

每次重新计算都从一个安全的默认状态开始，某条指令需要时再覆盖。比如普通算术不写内存，所以默认 `mem_we=0`；SW 合法且对齐时才把它改为 1。

假如组合块的某个分支没有给 `mem_we` 赋值，工具可能需要保留上一次值，推断出锁存器。对 CPU 来说，那可能让一次 Store 的使能延续到下一条指令。写完组合译码，不仅要看语法通过，还要检查每条路径是否有明确定义。

## 2.5 ADD、SUB 和立即数

R 型 ADD/SUB 使用两个源寄存器；opcode 相同，`funct7` 区分：

```systemverilog
if (f3 == 0 && (f7 == 0 || f7 == 7'h20)) begin
    result = f7 == 0 ? a + b : a - b;
    write_rd = 1;
end else bad = 1;
```

只写 `if (f7[5])` 不够：其他保留的 `funct7` 也可能 bit 5 为 1，结果会把非法编码误当成 SUB。项目支持 M、Zba、Zbb，还需要比本例更完整的合法性判断；我们会在第 5 章逐项建立。

LUI 的结果由指令高 20 位和低 12 个零组成。它不读取 rs1；即使那一段物理比特看起来像寄存器编号，也不能因此制造数据依赖。到了流水线和双发射，`use_rs1/use_rs2` 的区别尤其重要。

## 2.6 为什么分支立即数看起来被打乱了

BEQ/BNE 的相对偏移在指令中的位不是连续的。本例重组为：

```systemverilog
wire [31:0] imm_b = {{19{insn[31]}}, insn[31], insn[7],
                     insn[30:25], insn[11:8], 1'b0};
```

把 `imm_b` 与**这条分支自己的 PC**相加才得到目标。循环中，分支位于 `0x10`，目标是 `0x08`，所以偏移是 -8。条件成立时 next PC 为 8，不成立时沿用默认的 0x14。

即使 B 型编码的最低位固定为 0，本实验不支持 C 扩展，所以实际发生的跳转还须满足 4 字节对齐。如果条件不成立，不会因为一个没有采用的目标不对齐而停机。正式实现对这种情况应产生规定的异常，而本例只停机。

## 2.7 Store 的立即数与寄存器字段

`sw x1,0(x0)` 需要两个源寄存器：`x0` 是地址基址，`x1` 是要存的数据。因此不能像 I 型那样把整个 `insn[31:20]` 当偏移；其中一部分给 rs2 用了。S 型立即数分成：

```systemverilog
wire [31:0] imm_s = {{20{insn[31]}}, insn[31:25], insn[11:7]};
```

`insn[11:7]` 在 ADDI 中是 rd，在 SW 中却是立即数的低位；不能因为硬件一直提取了 `rd=insn[11:7]` 就认为 SW 需要写寄存器。控制信号决定这一字段在当前指令中是否有意义。

## 2.8 JAL 为什么还要写寄存器

函数调用结束要知道回到哪里。`jal x5,done` 把当前 PC+4 写进 x5，同时转移到相对目标。你可以把它理解成同时做两件事：

```text
x5 ← 当前 PC + 4
PC ← 当前 PC + 立即数
```

目标不对齐时，本实验设置 `bad`，既不改变 PC，也不写链接地址。正式项目采用架构异常路径，而不是永久停机。

## 2.9 机器码是怎么核对出来的

测试台中直接写了十六进制机器码，避免让第一次实验依赖交叉编译器。如果已经装有 RISC-V GNU 工具链，可以在 WSL 中复核：

```bash
riscv64-unknown-elf-as -march=rv32i -mabi=ilp32 \
  -o /tmp/sum.o examples/02-single-cycle/sum.S
riscv64-unknown-elf-objdump -d -M no-aliases /tmp/sum.o
```

工具前缀是 `riscv64`，但 `-march=rv32i -mabi=ilp32` 指定了 RV32 目标。看 `bne` 的偏移和 `jal` 的目标时，注意反汇编可能用 ABI 名字（例如 `ra` 是 x1、`sp` 是 x2）。测试台的 ROM 数值已用这个工具链核对。

## 2.10 接下来缺的不是“多加几条 case”

现在的 `LW` 假定 `mem_addr` 一产生，`mem_rdata` 在同一周期就可用。但项目里的 TCM 是同步读，外部存储还会等待。若数据晚两拍，这个核心会在第一个时钟沿把旧数据写进 rd。

所以从这里迈向真实项目的第一步，不是继续往 case 堆指令，而是区分“发起请求”和“收到响应”。[第 3 章](03-让内存等待.md)先写一个会等待的 RAM；在真实核心中，我们还要保存属于该请求的 PC、地址、目的寄存器和异常状态。
