# 17. 从小 CPU 跨到真实接口：手写一个会等待的核心

如果你读到第 16 章，仍然觉得“我知道要有握手和流水线，却不知道第一个能运行的 core 应该怎么拼”，这一章是中间台阶。我们把第 2 章的求和程序接到一个真正的**请求/响应**接口，并复用仓库译码器与 ALU。这个例子有完整的可编译源码和自检，但故意不做双发射与流水重叠。

**重要边界**：它是多周期教学核心，不是完整青龙，也不是完整 RV32I 系统。它不实现 M、CSR、中断或真正的架构陷阱；错误和未支持操作只会置 `fault` 并停机。它使用现有项目模块，不能算一份独立完成的译码器/ALU。下一步仍须按第 16 章把它扩展为流水化完整项目，并与真实 RTL 比较。

## 17.1 为什么要增加这一步

第 2 章的 CPU 将内存读视为组合逻辑：当地址变化时，数据随之出现。这使例子短，但很难直接连接同步 FPGA RAM 和延迟外设。

这次我们要求：

```text
取指：先等待请求被接受，再等待响应被接受。
访存：先保存该指令上下文，等待请求被接受，再等待响应。
中间可以停任意多拍；没有握手时不可悄悄跳到下一条。
每条正常指令只产生一次退休脉冲。
```

在不考虑中断、取消和全速流水时，一个多周期状态机最适合建立直觉：任何时刻最多处理一条架构指令，不会有数据旁路和同拍两条的年龄问题。慢没有关系，先保证正确。

## 17.2 文件及运行命令

- 核心源码：[multicycle_core.sv](examples/09-multicycle-core/multicycle_core.sv)
- 自检测试台：[multicycle_tb.sv](examples/09-multicycle-core/multicycle_tb.sv)
- 使用项目的 [rv32_pkg.sv](../rtl/rv32_pkg.sv)、[rv32_decode.sv](../rtl/rv32_decode.sv) 与 [rv32_alu.sv](../rtl/rv32_alu.sv)

在项目根目录执行：

```powershell

if ($LASTEXITCODE -ne 0) { throw '仿真失败' }
```

本次实际结果：

```text

```

Icarus 可能提示 `constant selects in always_* processes are not fully supported` 并扩大敏感度；这里仿真仍成功。若出现语法错误、fatal、超时或其他警告，不要一律忽略。

## 17.3 本例支持什么，不支持什么

它可以通过现有译码和 ALU处理普通的 LUI、AUIPC、算术/逻辑、条件分支、JAL/JALR，以及对齐的字节/半字/字 Load/Store。现有 ALU 也包含部分位操作，但这个例子没有为所有指令逐一证明覆盖。

它明确拒绝 M 乘除、CSR、ECALL/EBREAK/MRET、FENCE.I 和其他 serial 指令；非法指令、请求错误、目标或访存地址不对齐时进入 HALT。没有 `mepc/mcause/mtval`，没有错误恢复，也没有预测、取指队列或第二退休口。测试只运行一个短程序，不能证明全部被译码指令均无 bug。

这份边界在你自己改程序时很重要：看到 FENCE 后停机是本例的简化行为，不是青龙项目应有行为。

## 17.4 从状态图开始写代码

```text
             请求接收                 响应接收
IF_REQ ─────────────────→ IF_RSP ─────────────────→ EXEC
  ▲                                                    │
  │                普通 ALU/分支成功，退休              │
  └────────────────────────────────────────────────────┤
                                                       │ Load/Store
                                                       ▼
                        请求接收                  响应接收
                     D_REQ ─────────→ D_RSP ───────────────→ IF_REQ
                                                        │
                    非法/不对齐/响应错误 ───────────────→ HALT
```

`IF_REQ` 只负责请求，不在这时假定读回了指令。`IF_RSP` 只在 `i_rsp_valid && i_rsp_ready` 时把低 32 位保存到 `instruction`；第二字在这个实验中不用。

进入 `EXEC` 后，如果是普通算术/跳转，计算结果并退休；如果是访存，把本条指令必要字段保存到 `pending_*` 再发请求。`D_RSP` 得到成功响应之后才退休。发生错误进入 HALT；这是教学简化，不是项目陷阱流程。

## 17.5 写取指请求

先定义输出：

```systemverilog
assign i_req_valid = (state == IF_REQ) && !rst;
assign i_req_addr = pc;
assign i_rsp_ready = (state == IF_RSP) && !rst;
```

请求被接受才转等待：

```systemverilog
IF_REQ: if (i_req_valid && i_req_ready) state <= IF_RSP;
```

如果 ready 低，状态保持 IF_REQ，PC 没变，请求也继续显示相同地址。这个教学核心没有前端分支重定向重叠，所以不需要演示“接受前可取消”；实际项目接口允许取指请求在接受前取消，适配其他总线时必须考虑差异。

在 IF_RSP 中等待 `i_rsp_valid && i_rsp_ready`。响应错误则 fault；成功则捕获指令并进入 EXEC。这样即使响应延迟 10 拍也能保持对应关系，因为本核心等待期间 PC 不变；完整项目允许前端继续准备新地址，因此必须额外保存 `q_pc`。

## 17.6 接现有译码器与 ALU

```systemverilog
import rv32_pkg::*;
decode_t dec;
rv32_decode decoder(.insn(instruction), .decoded(dec));
rv32_alu alu(.op(dec.alu), .a(alu_a), .b(alu_b), .result(alu_result));
```

选择两个操作数：

```systemverilog
a = dec.rs1 == 0 ? 0 : regs[dec.rs1];
b = dec.rs2 == 0 ? 0 : regs[dec.rs2];
alu_a = dec.src_pc ? pc : a;
alu_b = dec.src_imm ? dec.imm : b;
```

ALU 不负责决定 PC，也不知道结果是否要写 rd：它只根据 `op` 计算结果。例如 AUIPC 使用 PC 和立即数作为 ALU 输入；分支要额外比较 a/b；JAL/JALR 的写回值是 `PC+4`，不是目标地址。

`x0` 每次读取强制为 0，写回时也检查 `rd!=0`；其他寄存器没有复位。测试程序必须在读取普通寄存器之前初始化它们。

## 17.7 写分支与跳转

`dec.branch` 为真时，根据 funct3 分别比较相等、有符号大小或无符号大小；JAL 和 JALR 则无条件 taken。

```systemverilog
target = dec.jalr ? ((a + dec.imm) & 32'hfffffffe) : pc + dec.imm;
next_pc = taken ? target : pc + 4;
```

JALR 目标先清 bit 0；本例不支持压缩指令，因此真正跳转的目标仍须 4 字节对齐。没有 taken 的条件分支不应因未使用目标不对齐而失败。

在项目完整核心里，真实下一 PC 还需与预测值比较；本例没有并行预取，直接在执行完本条后更新 PC 就够了。

## 17.8 要发内存请求时，先冻结这条指令

进入 D_REQ 之前，我们保存：

```systemverilog
pending_pc      <= pc;
pending_insn    <= instruction;
pending_addr    <= addr;
pending_data    <= b;
pending_next    <= pc + 4;
pending_rd      <= dec.rd;
pending_funct3  <= dec.funct3;
pending_load    <= dec.load;
pending_store   <= dec.store;
state           <= D_REQ;
```

为什么不能等响应回来时再看 `dec`？这个多周期实验在等待时 `instruction` 暂时不会变化，所以似乎还可行；但一旦改成流水线，EX 里可能已经是下一条。先按“结果必须和自己的上下文绑定”来设计，迁移时就不会把新指令的 rd 或宽度误配给旧响应。

对齐失败在保存/发请求前直接 fault：半字检查 `addr[0]`，字检查 `addr[1:0]`。本例不拆分跨界访问。请注意 `fault` 只是停止，不是正确的 trap 架构状态。

## 17.9 地址、数据与 byte strobe

先对齐总线地址：

```systemverilog
assign d_req_addr = {pending_addr[31:2], 2'b0};
assign d_req_wdata = pending_data << {pending_addr[1:0], 3'b0};
```

写使能按宽度生成：

```systemverilog
case (pending_funct3[1:0])
    0: d_req_wstrb = 4'b0001 << pending_addr[1:0];
    1: d_req_wstrb = 4'b0011 << pending_addr[1:0];
    default: d_req_wstrb = 4'b1111;
endcase
```

一个地址为 `0x102` 的 `SB`，数据低字节为 `0x7f`，请求应为 `addr=0x100, wdata=0x007f0000, wstrb=0100`。实际内存仅在请求握手时写选中的字节；等待 ready 时不能重复写。

这个实验无分支重定向和更老异常并发，因此只需在 D_REQ 保持已保存载荷；完整流水线的 early LSU 必须再加入 hazard、较老异常等门控，见第 9 章。

## 17.10 响应回来后怎样还原 Load

```systemverilog
shifted = d_rsp_data >> {pending_addr[1:0], 3'b0};
case (pending_funct3)
    0: load_result = {{24{shifted[7]}}, shifted[7:0]};
    1: load_result = {{16{shifted[15]}}, shifted[15:0]};
    4: load_result = {24'b0, shifted[7:0]};
    5: load_result = {16'b0, shifted[15:0]};
    default: load_result = d_rsp_data;
endcase
```

响应只在 `state==D_RSP` 时接收。Load 成功后写 `pending_rd` 并退休；Store 成功响应后以 rd=0 退休。若响应报错，进入 HALT，Load 不写目的寄存器。

外设 Store 的副作用通常在请求被设备接受时发生，不是等退休时才发生；错误响应可能发生在副作用之后。真实系统必须制定设备错误契约和精确异常策略，不能假设本实验自动提供回滚。

## 17.11 测试台做了什么

测试台 ROM 放入第 2 章同一个机器码程序：从 5 加到 1，结果 15 写 RAM，再读回来，用条件分支和 JAL 跳过不应执行的指令。请求 ready 由周期数产生等待，取指和数据响应也分别延迟几拍；响应有效后保持到接收。

测试台还列出 23 次预期退休 PC，循环体每次依次为 `8、12、16`。每次 `retire_valid` 检查 PC，最终检查：

```text
退休数 23；Store 恰好 1 次；RAM[0]=15；
x1=15，x3=15，JAL 写回 x5=44，x6=44。
```

这比只检查最后的 RAM 多了一层控制流检查，但仍未检查所有退休数据、所有字节/半字情况，也没覆盖各种错误。在你继续开发前，应该补充：请求长期背压时地址/写数据稳定断言；不同 lane 的 LB/LBU/LH/LHU/SB/SH；错误响应后没有寄存器写回；非法指令和不对齐不发请求。

## 17.12 这个状态机如何变成流水线

不要突然把 `case(state)` 删掉然后把所有代码放进一个组合块。先明确变化：

1. **IF** 与 **EX** 不再互斥，取指时 EX 可以执行另一条；因此必须给请求保存 `q_pc`、给已返回指令准备有效缓冲。
2. **EX** 与 **MEM** 可以同时装两条；pending 上下文变成带 `m_valid` 的 MEM 流水寄存器。
3. WB 保存结果并生成退休；如果 MEM 未完成，EX 必须保持，而不是覆盖它。
4. 两条指令可能出现依赖，先保守暂停，再增加旁路。
5. EX 中的分支改变 PC 时，较年轻前端数据和已在途响应要清理或作废。
6. 加入异常/中断后，较老指令的异常必须压制年轻指令的副作用。
7. 再引入队列两项发射、物理通道交换以及顺序双退休。
